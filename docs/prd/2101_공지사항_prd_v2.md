## Executive Summary

The Notice Board (공지사항) module provides a unified platform for internal organizational communication through typed posts (notifications, sharing, directives, suggestions, open discussion), threaded comments, and file attachments. This v2 reflects final design decisions from the PRD review cycle, resolving 15 architectural and implementation topics. All decisions prioritize security, maintainability, and Phase 1 MVP feasibility.

**Key Changes from v1:**
- Soft-delete cascade strategy confirmed (HIGH priority)
- File upload security hardened with magic number validation (HIGH priority)
- 8 MEDIUM priority topics resolved with pragmatic Phase 1 decisions
- 5 LOW priority topics documented with default implementations

## 1. Overview

본 PRD는 sunjin-erp 시스템의 "공지사항 (게시판)" 기능에 대한 요구사항을 정의한다. 이 기능은 다양한 유형(공지, 공유, 지시, 건의, 자유)의 게시물을 분류하여 게시하고, 조회수 통계 및 댓글/답글 피드백 기능을 통해 조직 내 의사소통을 촉진하는 게시판 시스템을 제공한다.

**대상 모듈:** 공지사항 (게시판)
**대상 사용자 역할:** USER (조회, 댓글 작성), MANAGER (신규 게시물 작성, 자신의 게시물 수정), ADMIN (전체 관리 및 삭제)
**Phase:** Phase 1 (MVP: core functionality), Phase 2 (notifications, analytics, recovery features)

## 2. Goals & Objectives

* **조직 내 의사소통 증진:** 다양한 유형의 공지사항을 통일된 플랫폼에서 관리하여 정보 전달 효율성 향상
* **유형별 게시판 분류:** 공지, 공유, 지시, 건의, 자유 게시판으로 구분하여 정보 체계화
* **조회수 및 인기도 추적:** 게시물별 조회수를 세션 기반 중복 제외 방식으로 추적하여 핫이슈 파악 및 사용자 관심도 측정
* **양방향 피드백 시스템:** 댓글 및 답글(2단계 깊이 제한) 기능으로 게시물에 대한 질의응답 및 토론 지원
* **권한 기반 콘텐츠 관리:** 게시물 작성/수정/삭제 권한을 명확히 정의하여 무분별한 게시 방지
* **검색 및 필터링:** 게시판 유형, 작성자, 작성 날짜 등으로 쉽게 필터링하고 LIKE 기반 검색으로 필요한 정보 빠르게 접근
* **실시간 업데이트:** 새로운 게시물, 댓글 추가 시 목록 자동 갱신 (TanStack Query)
* **보안된 파일 업로드:** 매직 바이트 검증을 포함한 강화된 파일 보안

## 3. User Stories / Use Cases

* **US-1:** 일반 사용자로서, 공지사항 목록을 조회하고 게시판 유형(공지, 공유, 지시, 건의, 자유)으로 필터링할 수 있다. 그래서 필요한 정보를 빠르게 찾을 수 있다.
    * *Acceptance Criteria:*
        * 공지사항 목록 페이지에 모든 유형의 게시물 표시 (최신순)
        * 게시판 유형별 탭 또는 필터 제공
        * 게시물에 제목, 작성자, 작성일, 조회수, 댓글 수 표시
        * 페이지네이션 지원 (20개 항목 기본, 최대 100)
        * 정렬 지원: 최신순, 조회수순, 댓글순

* **US-2:** 일반 사용자로서, 게시물 상세 정보를 조회하고 댓글을 작성할 수 있다. 그래서 다른 직원들과 소통할 수 있다.
    * *Acceptance Criteria:*
        * 게시물 상세 페이지에 제목, 내용, 작성자, 작성일, 수정일, 수정자, 조회수, 게시판 유형 표시
        * 첨부파일 다운로드 링크 제공 (이미지, PDF, 문서 등)
        * 댓글 목록 표시 (시간순 오래된순, 페이지네이션)
        * 댓글 작성 폼 제공 (작성자 자동 입력, 내용 텍스트에어리어)
        * 댓글 작성 시 실시간 목록 갱신

* **US-3:** 일반 사용자로서, 댓글에 대한 답글(대댓글)을 작성할 수 있다. 그래서 특정 댓글에 대한 피드백을 줄 수 있다.
    * *Acceptance Criteria:*
        * 각 댓글에 "답글 작성" 버튼 제공 (최상위 댓글에만, 답글에는 버튼 미표시)
        * 답글 폼은 댓글 바로 아래에 인라인으로 표시
        * "@원댓글작성자" 멘션 자동 추가 in reply form (선택, 텍스트로 저장)
        * 답글은 원댓글 아래 들여쓰기로 표시 (최대 1단계, 답글의 답글은 불가)
        * 실시간 갱신
        * 답글 작성 시 parent_comment_id 유효성 검증 (HTTP 400 if violates depth constraint)

* **US-4:** 매니저로서, 새로운 게시물을 작성할 수 있다. 그래서 팀 또는 조직에 정보를 공유할 수 있다.
    * *Acceptance Criteria:*
        * 게시물 작성 폼에서 게시판 유형, 제목, 내용 입력
        * 내용은 기본 텍스트 에디터 (WYSIWYG은 Phase 2)
        * 파일 첨부 가능 (최대 5개, 각 10MB 제한)
        * 파일 검증: 매직 바이트 기반 타입 검증, 허용 타입: JPEG, PNG, GIF, PDF, DOCX, PPTX
        * 미리보기 기능 제공
        * 작성 시 작성자, 작성일 자동 입력
        * 임시 저장 기능 (localStorage)

* **US-5:** 매니저로서, 자신이 작성한 게시물을 수정하고 삭제할 수 있다. 그래서 게시된 정보를 관리할 수 있다.
    * *Acceptance Criteria:*
        * 자신의 게시물에 "수정", "삭제" 버튼 표시
        * 수정 시 기존 내용이 폼에 로드되어 편집 가능
        * 수정 완료 시 "수정일", "수정자" 업데이트
        * 삭제 시 확인 대화 표시
        * 삭제는 soft delete (deleted_at 설정, 연관 댓글/첨부파일 cascade soft delete)

* **US-6:** 사용자로서, 자신이 작성한 댓글을 수정하고 삭제할 수 있다.
    * *Acceptance Criteria:*
        * 자신의 댓글에 "수정", "삭제" 버튼 표시
        * 다른 사용자의 댓글은 버튼 비활성화 (ADMIN 제외)
        * 수정 시 인라인 textarea에서 편집, Save/Cancel 버튼 표시
        * 삭제 시 확인 대화 표시 (soft delete)
        * 수정된 댓글: "(edited)" 배지 표시, 호버 시 수정 시각 표시

* **US-7:** 관리자로서, 모든 게시물을 조회하고 필요시 삭제할 수 있다. 그래서 부적절한 콘텐츠를 관리할 수 있다.
    * *Acceptance Criteria:*
        * 게시물 목록에 관리 필터 제공 (삭제된 게시물 보기 옵션, ADMIN만)
        * 모든 게시물에 "삭제" 버튼 표시 (soft delete)
        * 삭제 이유 입력 옵션 (선택)
        * 삭제 이력 기록 (Phase 2)

* **US-8:** 일반 사용자로서, 게시물을 검색할 수 있다. 그래서 특정 주제의 게시물을 찾을 수 있다.
    * *Acceptance Criteria:*
        * 목록 페이지에 검색 입력창 제공
        * 제목, 내용, 작성자로 LIKE 기반 검색 가능 (debounce 300ms)
        * 검색 결과는 목록에 실시간 반영 (최신순 정렬)
        * 검색 조건 초기화 버튼 제공
        * 검색은 삭제되지 않은 게시물만 대상 (deleted_at IS NULL)

* **US-9:** 관리자로서, 공지사항 통계를 조회할 수 있다. 그래서 게시판 활동 현황을 파악할 수 있다.
    * *Acceptance Criteria:*
        * 게시판 유형별 게시물 수 표시
        * 최근 7일 게시물 수 추이 차트 (선택, Phase 2)
        * 상위 조회수 게시물 TOP 5 표시
        * 활동성 있는 사용자 순위 (댓글 작성 수 기반)

## 4. Scope

### 4.1 In-Scope

* **Notice (게시물) Entity**
    - 기본 정보: 제목(title), 내용(content), 게시판 유형(type: 공지/공유/지시/건의/자유)
    - 메타데이터: 작성자(author_id FK), 작성일(created_at), 수정자(updated_by_id FK, nullable), 수정일(updated_at), 조회수(view_count)
    - 메타데이터: 소프트 삭제(deleted_at), 삭제 이유(deletion_reason, nullable)
    - Unique constraint 없음 (동일 제목 중복 허용)

* **NoticeAttachment (게시물 첨부파일) Entity**
    - 게시물 FK, 파일명(filename), 파일 경로(file_path), 파일 크기(file_size), MIME 타입(mime_type)
    - 메타데이터: 업로드일(uploaded_at), 소프트 삭제(deleted_at)
    - 당 게시물이 soft-delete되면 cascade soft-delete

* **Comment (댓글) Entity**
    - 게시물 FK, 내용(content), 작성자(author_id FK)
    - 메타데이터: 작성일(created_at), 수정일(updated_at), 소프트 삭제(deleted_at)
    - 부모 댓글 FK (parent_comment_id, nullable, 답글용)
    - 최대 깊이: 2단계 (댓글 → 답글), 답글의 답글은 불가
    - 당 게시물이 soft-delete되면 cascade soft-delete

* **API Route Handlers (12개)**
    - Notice: GET (list, detail), POST (create), PUT (update), DELETE (soft delete with cascade)
    - Attachment: GET (download), DELETE (soft delete)
    - Comment: GET (list by notice), POST (create with depth validation), PUT (update), DELETE (soft delete)
    - Statistics: GET (notice count, popular posts, user activity)

* **Frontend Pages & Components**
    - 공지사항 목록 페이지 (`/notices`)
    - 게시물 상세 페이지 (`/notices/[id]`, ISR-enabled)
    - 게시물 작성 페이지 (`/notices/new`)
    - NoticeList 컴포넌트 (게시물 테이블, 필터, 검색)
    - NoticeForm 컴포넌트 (작성/수정 폼, 파일 업로드)
    - NoticeDetail 컴포넌트 (상세 정보 + 댓글, Server Component)
    - CommentSection 컴포넌트 (댓글 목록 + 작성 폼)
    - NoticeStatistics 컴포넌트 (통계 대시보드, Phase 2)

* **TanStack Query Hooks**
    - `useNotices()` — 목록 조회 (유형별, 검색 포함, session-based view deduplication)
    - `useNotice(id)` — 상세 조회
    - `useCreateNotice()` — 신규 작성 mutation (invalidates notices-list, revalidates detail page)
    - `useUpdateNotice(id)` — 수정 mutation (invalidates detail, revalidates ISR)
    - `useDeleteNotice(id)` — 삭제 mutation (cascade soft-delete comments/attachments)
    - `useComments(noticeId)` — 댓글 목록 조회
    - `useCreateComment(noticeId)` — 댓글 작성 mutation (with depth validation)
    - `useUpdateComment(commentId)` — 댓글 수정 mutation
    - `useDeleteComment(commentId)` — 댓글 삭제 mutation
    - `useNoticeStatistics()` — 통계 조회 (Phase 2)

* **역할 기반 접근 제어 (RBAC)**
    - USER: 조회 및 댓글/답글 작성만 가능
    - MANAGER: USER 권한 + 게시물 작성/수정/삭제 (자신의 게시물만, owner-based only)
    - ADMIN: 모든 게시물/댓글 조회/삭제 가능, 통계 조회 가능
    - 권한 검증: 항상 현재 세션의 role 기반 (creation-time role 아님)

* **유효성 검증**
    - 제목: 필수, 5~200자
    - 내용: 필수, 최소 10자, 최대 10,000자
    - 게시판 유형: 필수, enum (공지/공유/지시/건의/자유)
    - 파일: 최대 5개, 각 10MB, 매직 바이트 검증 (JPEG, PNG, GIF, PDF, DOCX, PPTX만 허용)
    - 댓글: 필수, 최소 1자, 최대 1000자

* **검색 및 필터링**
    - 게시판 유형으로 필터링 (탭 또는 드롭다운)
    - 작성 날짜 범위 (선택)
    - 작성자 필터 (선택)
    - 제목/내용 검색 (LIKE 기반, 실시간 debounce 300ms, 최신순 정렬)
    - 정렬: 최신순, 조회수순, 댓글순

* **조회수 추적 (Session-Based Deduplication)**
    - 게시물 상세 조회 시 조회수 +1 증가 (async, non-blocking)
    - 같은 사용자 반복 조회는 session-based 중복 제외 (same session = 1 count, new session = recount)
    - 조회수 verification query: 통계 대시보드에서 수동 점검 (Phase 2)

* **캐시 무효화 전략**
    - 게시물 추가/수정/삭제 시: notices-list 캐시 무효화, detail page ISR revalidate
    - 댓글 추가/수정/삭제 시: notices-detail (comments 섹션) 캐시 무효화
    - 조회수 업데이트는 캐시 무효화 미포함 (실시간 카운트)

* **Unit Testing**
    - API Route 테스트 (CRUD, 권한 검증, cascade soft-delete)
    - Comment 계층 검증 테스트 (최대 2단계 깊이 체크)
    - 파일 업로드 테스트 (MIME 검증, 매직 바이트 검증)
    - 파일 다운로드 테스트 (권한 검증, deleted attachment 404)

## 5. Design Decisions (v2 - Mediation Outcome)

This section documents the 15 design decisions from the PRD review cycle. See separate document `2101_공지사항_prd_decisions.md` for detailed rationale.

### HIGH Priority Decisions

**Decision #1: Soft Delete Cascade Behavior** ✓
- When Notice is soft-deleted: automatically cascade soft-delete to Comments and Attachments
- Implementation: NoticeService.softDelete(noticeId) handles cascade
- Impact: All list queries use `WHERE deleted_at IS NULL` (clean orphan prevention)

**Decision #2: File Upload MIME Type Validation with Magic Numbers** ✓
- Validate using magic bytes (file signature), not client-provided MIME header
- Allowed types: JPEG, PNG, GIF, PDF, DOCX, PPTX (exclude SVG, DOC)
- Implementation: file-type library for magic byte detection
- Impact: Strong security against file spoofing and XSS attacks

### MEDIUM Priority Decisions

**Decision #3: Comment Depth Enforcement** ✓ — Application-level validation + UI prevention
**Decision #4: View Count Deduplication** ✓ — Session-based (increment once per session)
**Decision #5: Search Strategy** ✓ — LIKE-based substring search (no FTS in Phase 1)
**Decision #6: Notice Type Categorization** ✓ — Hardcoded enum (5 values)
**Decision #7: File Storage Strategy** ✓ — Local file system Phase 1, abstract for Phase 2 S3 migration
**Decision #8: Detail Page Rendering** ✓ — ISR (Incremental Static Regeneration) with Next.js 14
**Decision #9: Search Query Scope** ✓ — Exclude deleted notices only (revisit when employee soft-delete added)

### LOW Priority Decisions

**Decision #10: Comment Edit Indicator** ✓ — Show "(edited)" badge with timestamp on hover
**Decision #11: Pagination Strategy** ✓ — Fixed 20 default, max 100 (user preferences deferred)
**Decision #12: Edit Metadata Display** ✓ — Show "Updated by [name] on [date]" on detail page
**Decision #13: Comment Mentions (Phase 1 Pre-Decision)** ✓ — Auto-add @username (notifications Phase 2)
**Decision #14: Comment Sorting** ✓ — Fixed oldest-first (chronological thread order)
**Decision #15: Comment Edit UX** ✓ — Inline editing (textarea converts comment card)

## 6. Technical Considerations & Architecture Alignment

### 6.1 Next.js App Router Structure

* **Page Routes:**
    - `src/app/(main)/notices/page.tsx` — 게시물 목록 페이지 (Server Component)
    - `src/app/(main)/notices/new/page.tsx` — 게시물 신규 작성 페이지
    - `src/app/(main)/notices/[id]/page.tsx` — 게시물 상세 페이지 (Server Component, ISR-enabled)
    - `src/app/(main)/notices/[id]/loading.tsx` — 상세 페이지 로딩 스켈레톤

* **Layout:**
    - 공통 `src/app/(main)/layout.tsx` 사용 (사이드바, 헤더 포함)

* **Server vs Client Components:**
    - **Page:** Server Component (권한 검증, 초기 데이터 로딩, ISR revalidation)
    - **Form/Dialog:** Client Component (`'use client'` 지시어)
    - **List/Table:** Client Component (필터, 정렬, 페이지네이션)
    - **Detail:** Server Component fetches notice, Client Component hydrates with comments via TanStack Query

* **ISR Configuration (Decision #8):**
    - Detail page uses `revalidate = 3600` (revalidate on-demand or every 1 hour)
    - Notice mutation calls `revalidatePath('/notices/[id]')` to purge cache
    - Comments load client-side (dynamic, TanStack Query)

### 6.3 Database (Oracle XE 21c + Direct oracledb)

> **⚠️ 중요 변경사항 (2026-01-28):**
> TypeORM이 프로젝트에서 제거되었습니다. 모든 데이터베이스 작업은 `oracledb` 드라이버를 직접 사용합니다.
> - `src/lib/db-direct.ts`의 `executeQuery`/`executeUpdate` 함수 사용
> - Entity 클래스 대신 SQL 쿼리 직접 작성
> - Bind parameter (`:paramName`) 방식으로 SQL Injection 방지

**테이블 정의:**

```
NOTICE (게시물)
├── id (PK)
├── title (VARCHAR2, 최대 200자)
├── content (CLOB, 최대 10,000자)
├── type (VARCHAR2: 공지 | 공유 | 지시 | 건의 | 자유, CHECK constraint)
├── author_id (FK → EMPLOYEE, ON DELETE RESTRICT)
├── view_count (NUMBER, default: 0, async update)
├── created_at (TIMESTAMP)
├── updated_at (TIMESTAMP)
├── updated_by_id (FK → EMPLOYEE, nullable, ON DELETE SET NULL)
├── deleted_at (TIMESTAMP, soft delete)
├── deletion_reason (VARCHAR2, nullable)
└── Indexes:
    ├── PRIMARY KEY (id)
    ├── (type, created_at) — 유형별 + 날짜 필터링
    ├── (author_id, created_at) — 작성자별 이력
    ├── (created_at) — 최신순 정렬
    ├── (view_count DESC) — 조회수순 정렬 성능
    ├── (deleted_at) — soft delete 쿼리 최적화
    ├── (title) — search LIKE 성능 (or full-text if available)
    └── (content) — search LIKE 성능 (or full-text if available)

NOTICE_ATTACHMENT (첨부파일)
├── id (PK)
├── notice_id (FK → NOTICE, ON DELETE RESTRICT)
├── filename (VARCHAR2, original filename)
├── file_path (VARCHAR2, UUID-based path on disk)
├── file_size (NUMBER)
├── mime_type (VARCHAR2, validated via magic bytes)
├── uploaded_at (TIMESTAMP)
├── deleted_at (TIMESTAMP, soft delete, cascaded with Notice)
└── Indexes:
    ├── PRIMARY KEY (id)
    ├── (notice_id) — 게시물별 첨부파일 조회
    └── (deleted_at) — soft delete 쿼리

COMMENT (댓글)
├── id (PK)
├── notice_id (FK → NOTICE, ON DELETE RESTRICT)
├── content (VARCHAR2, 최대 1000자)
├── author_id (FK → EMPLOYEE, ON DELETE RESTRICT)
├── parent_comment_id (FK → COMMENT, nullable, ON DELETE RESTRICT, 답글용, 깊이 제한)
├── created_at (TIMESTAMP)
├── updated_at (TIMESTAMP)
├── deleted_at (TIMESTAMP, soft delete, cascaded with Notice)
└── Indexes:
    ├── PRIMARY KEY (id)
    ├── (notice_id, created_at) — 게시물별 댓글 조회 (oldest-first sort)
    ├── (notice_id, parent_comment_id, created_at) — 답글 트리 쿼리 (reply-only filter)
    ├── (author_id) — 작성자별 댓글
    ├── (parent_comment_id) — 부모 댓글 조회 (depth validation)
    └── (deleted_at) — soft delete 쿼리
```

**Constraints:**
- `ON DELETE RESTRICT` for author_id, notice_id (audit trail preservation)
- `ON DELETE SET NULL` for updated_by_id (optional update tracking)
- CHECK constraint on NOTICE.type: values in ('공지', '공유', '지시', '건의', '자유')
- Comment depth constraint: application-level validation enforces parent_comment_id.parent_comment_id = NULL

**Cascade Behavior (Decision #1):**
- When NOTICE.deleted_at is set (soft-delete):
  1. Update COMMENT SET deleted_at = NOW() WHERE notice_id = ? AND deleted_at IS NULL
  2. Update NOTICE_ATTACHMENT SET deleted_at = NOW() WHERE notice_id = ? AND deleted_at IS NULL
  3. Implemented in NoticeService.softDelete() method

### 6.4 State Management

* **Server State (TanStack Query):**
    - `notices-list`: 목록 조회 캐시 (staleTime: 5분, gcTime: 30분)
    - `notices-detail-{id}`: 상세 조회 캐시 (staleTime: 10분, gcTime: 30분) — ISR takes precedence
    - `notices-comments-{id}`: 댓글 목록 캐시 (staleTime: 3분, gcTime: 15분)
    - `notices-statistics`: 통계 캐시 (staleTime: 30분, gcTime: 60분)

* **Client State (Zustand, optional):**
    - 목록 페이지 필터 상태 (게시판 유형, 검색 입력, 정렬) — localStorage persist

* **Session State:**
    - viewed_notices: Set of notice IDs viewed in current session (for view count deduplication, Decision #4)

* **Form State (React Hook Form):**
    - 게시물 작성/수정, 댓글 작성 폼 상태

### 6.5 Authentication & Authorization

* **NextAuth.js:** Session 객체에 `user.role`, `user.id` 포함
* **Page-level:** 각 페이지 Server Component에서 세션 검증 (USER 이상 필수)
* **API-level:** 각 Route Handler에서 권한 검증
    - GET: USER 이상
    - POST (게시물): MANAGER 이상
    - PUT/DELETE (게시물): 자신의 게시물 (author_id == user.id) 또는 ADMIN
    - POST (댓글): USER 이상
    - PUT/DELETE (댓글): 자신의 댓글 (author_id == user.id) 또는 ADMIN
    - DELETE (첨부파일): ADMIN 또는 게시물 작성자 (notice.author_id == user.id)
* **Authorization Model:** Current session role is authoritative (not creation-time role). Demoted users lose privileges on old content.
* **Middleware:** `src/middleware.ts`에서 `/notices` 경로 보호
    - No session → redirect to /auth/login
    - Session exists, role < USER → return 403
    - Page-level checks for MANAGER+ routes (create/edit)

### 6.6 파일 업로드 및 다운로드

* **업로드 경로:** `./public/uploads/notices/{noticeId}/{filename}`
* **파일 제한:**
    - 최대 5개 파일
    - 각 파일 최대 10MB
    - MIME 타입 검증: 매직 바이트 기반
    - 허용 타입: image/jpeg, image/png, image/gif, application/pdf, application/vnd.openxmlformats-officedocument.wordprocessingml.document, application/vnd.openxmlformats-officedocument.presentationml.presentation (Decision #2)
* **보안:**
    - 파일명 sanitization: strip special chars except hyphen/underscore, max 100 chars
    - UUID 기반 파일명 생성 (원본 파일명은 DB에만 저장)
    - 매직 바이트 검증 (file-type library) — 클라이언트 MIME 헤더 신뢰 금지
    - SVG 파일 명시적 거부 (XSS 위험)
    - 다운로드 시 권한 검증: authenticated USER+, notice.deleted_at IS NULL, attachment.deleted_at IS NULL
    - 삭제된 첨부파일: return 404 (not found)

### 6.7 입력 검증 및 보안

* **Server-side 검증 (필수):**
    - 제목: 필수, 5~200자, XSS 방지
    - 내용: 필수, 최소 10자, 최대 10,000자, XSS 방지
    - 댓글: 필수, 최소 1자, 최대 1000자, XSS 방지
    - 게시판 유형: enum 검증 (5 hardcoded values only)
    - 파일: 매직 바이트 타입 검증, 크기 검증, 개수 제한
    - 댓글 깊이: parent_comment_id validation (HTTP 400 if depth > 2)

* **Client-side 검증:**
    - React Hook Form으로 실시간 피드백
    - Comment reply button: hide for level-2 comments (UX prevention)

* **XSS 방지:**
    - 댓글 내용 sanitization (DOMPurify)
    - 게시물 제목/내용: trusted (internal system), but sanitize on display

* **CSRF 방지:**
    - NextAuth.js 자동 처리

### 6.8 성능 최적화

* **API Response Time Target:** p95 < 200ms
* **Pagination:** 기본 20개, 최대 100개
* **Index Strategy:**
    - `NOTICE(type, created_at)` — 유형별 + 날짜 필터링
    - `NOTICE(author_id, created_at)` — 작성자별 이력
    - `NOTICE(view_count DESC)` — 조회수순 정렬
    - `NOTICE(created_at)` — 최신순 정렬
    - `NOTICE(title, content)` — search LIKE 성능
    - `COMMENT(notice_id, created_at)` — 게시물별 댓글 조회 (oldest-first)
    - `COMMENT(notice_id, parent_comment_id, created_at)` — 답글 트리 쿼리
    - `NOTICE_ATTACHMENT(notice_id)` — 첨부파일 조회

* **Lazy Loading:**
    - 첨부파일은 상세 페이지에서만 로드
    - 댓글은 별도 쿼리 (list에 포함 안 함, TanStack Query pagination)

* **View Count Update:**
    - 비동기 업데이트 (응답 지연 없음, fire-and-forget)
    - 세션 기반 중복 제외 (Decision #4)
    - 실패 로깅 (에러 큐)

* **Cache Strategy:**
    - List page: ISR not used (dynamic filtering)
    - Detail page: ISR with on-demand revalidation (Decision #8)
    - Comments: TanStack Query with 3-min staleTime

### 6.9 API 구현 패턴 (Direct oracledb)

모든 API Route Handler는 아래 패턴을 따릅니다:

```typescript
import { executeQuery, executeUpdate } from '@/lib/db-direct';

// 조회 (SELECT)
const notices = await executeQuery<NoticeRow>(
  `SELECT n."id" as ID, n.TITLE, n.CONTENT, n.TYPE, n.VIEW_COUNT,
          n."created_at" as CREATEDAT, n."updated_at" as UPDATEDAT,
          e."name" as AUTHORNAME
   FROM NOTICE n
   LEFT JOIN EMPLOYEE e ON n.AUTHOR_ID = e."id"
   WHERE n."deleted_at" IS NULL
   ORDER BY n."created_at" DESC`,
  {}
);

// 생성 (INSERT)
const newId = await executeUpdate(
  `INSERT INTO NOTICE (TITLE, CONTENT, TYPE, AUTHOR_ID, VIEW_COUNT, "created_at", "updated_at")
   VALUES (:title, :content, :type, :authorId, 0, SYSTIMESTAMP, SYSTIMESTAMP)`,
  { title, content, type, authorId }
);

// 수정 (UPDATE)
await executeUpdate(
  `UPDATE NOTICE SET TITLE = :title, CONTENT = :content, "updated_at" = SYSTIMESTAMP
   WHERE "id" = :id AND "deleted_at" IS NULL`,
  { title, content, id }
);

// 소프트 삭제 (Soft Delete with Cascade)
await executeUpdate(
  `UPDATE NOTICE SET "deleted_at" = SYSTIMESTAMP WHERE "id" = :id`,
  { id }
);
await executeUpdate(
  `UPDATE COMMENT SET "deleted_at" = SYSTIMESTAMP WHERE NOTICE_ID = :id AND "deleted_at" IS NULL`,
  { id }
);
await executeUpdate(
  `UPDATE NOTICE_ATTACHMENT SET "deleted_at" = SYSTIMESTAMP WHERE NOTICE_ID = :id AND "deleted_at" IS NULL`,
  { id }
);
```

### 6.10 컬럼 식별자 규칙 (Oracle)

Oracle은 컬럼명을 **UPPERCASE로 자동 변환**합니다. 혼합 케이스 컬럼은 따옴표(`"`)로 감싸야 합니다:

| 테이블 | quoted (lowercase) | unquoted (UPPERCASE) |
|--------|-------------------|----------------------|
| **NOTICE** | `"id"`, `"created_at"`, `"updated_at"`, `"deleted_at"` | `TITLE`, `CONTENT`, `TYPE`, `AUTHOR_ID`, `UPDATED_BY_ID`, `VIEW_COUNT`, `DELETION_REASON` |
| **COMMENT** | `"id"`, `"created_at"`, `"updated_at"`, `"deleted_at"` | `NOTICE_ID`, `CONTENT`, `AUTHOR_ID`, `PARENT_COMMENT_ID` |
| **NOTICE_ATTACHMENT** | `"id"`, `"deleted_at"` | `NOTICE_ID`, `FILENAME`, `FILE_PATH`, `FILE_SIZE`, `MIME_TYPE`, `UPLOADED_AT` |
| **EMPLOYEE** (조인용) | `"id"`, `"name"`, `"email"`, `"created_at"`, `"updated_at"`, `"deleted_at"` | `EMPLOYEE_NUMBER`, `PHONE`, `DEPARTMENT_ID`, `ROLE`, `PASSWORD_HASH` |

**조인 예시:**
```sql
-- NOTICE와 EMPLOYEE 조인 시
SELECT n."id" as ID, n.TITLE, e."name" as AUTHORNAME
FROM NOTICE n
LEFT JOIN EMPLOYEE e ON n.AUTHOR_ID = e."id"
WHERE n."deleted_at" IS NULL
```

## 9. Security Considerations

* **Authentication:** NextAuth.js session 기반, 모든 API 호출 전 세션 검증
* **Authorization:**
    - USER: 조회, 댓글/답글 작성만
    - MANAGER: USER 권한 + 게시물 작성/수정/삭제 (자신의 게시물만, owner-based)
    - ADMIN: 모든 권한
    - API 레벨에서 권한 검증 (프론트엔드 숨김만으로 불충분)
    - 권한 검증: 항상 현재 세션 role 기반 (creation-time role 아님)

* **XSS 방지:**
    - 댓글 내용 sanitization (DOMPurify)
    - 게시물 제목/내용: trusted (internal system), sanitize on display

* **File Security (Decision #2 - Enhanced from v1):**
    - 매직 바이트 검증 (file-type library)
    - MIME 타입 whitelist: JPEG, PNG, GIF, PDF, DOCX, PPTX (SVG/DOC excluded)
    - 파일 크기 제한 (각 10MB, 총 5개)
    - 파일 저장 경로 격리 (./public/uploads/notices/)
    - 파일명 sanitization (특수 문자 제거, UUID 저장명)
    - 다운로드 시 권한 검증 + deleted_at 체크

* **Input Validation:**
    - Server-side 검증 필수 (모든 입력값)
    - SQL Injection 방지: oracledb bind parameters (`:paramName` 문법)
    - CSRF 방지: NextAuth.js 자동 처리
    - Comment depth validation: 2단계 이상 불가

* **Data Protection:**
    - 게시물 및 댓글은 민감 정보 취급 (internal system)
    - 작성자 정보는 표시 (감사 추적)
    - Soft delete 원칙: 물리 삭제 금지

* **Cascade Delete Prevention:**
    - ON DELETE RESTRICT for author_id, notice_id
    - Soft delete cascade (Notice → Comments/Attachments)
    - No hard delete in Phase 1
