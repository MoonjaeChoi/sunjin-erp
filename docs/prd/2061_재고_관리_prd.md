# Product Requirement Document: 재고 관리

문서번호: 2061
작성일: 2026-01-25
상위문서: 1000_초안.prd, 2001_전체_레이아웃_설정_prd_v2.md

## 1. Overview

본 PRD는 sunjin-erp 시스템의 "재고 관리" 기능에 대한 요구사항을 정의한다.
이 기능은 회사 내 IT 장비(모니터, 네트워크 장비, 소프트웨어 등)의 입출고 현황을 추적하고, 각 장비의 위치와 이동 이력을 관리하는 통합 인벤토리 시스템을 구축한다.

**대상 모듈:** 재고 관리 (Inventory Management)
**대상 사용자 역할:** USER / MANAGER / ADMIN
**주요 기능:** 장비 카테고리별 조회, 시리얼 번호 기반 추적, 위치 관리, 입출고 이력

## 2. Goals & Objectives

*   **장비 인벤토리 시각화:** 전사 장비의 현황을 카테고리, 모델명, 시리얼 번호 기반으로 조회하여 재고 파악의 정확성을 높인다.
*   **위치 추적:** 각 장비의 보관 위치 및 출고 위치를 실시간으로 관리하여 필요 시 신속한 장비 검색을 가능하게 한다.
*   **이력 관리:** 장비 입고, 출고, 이동 내역을 시간순으로 기록하여 추후 감사(audit) 및 사용처 추적을 지원한다.
*   **효율적인 조회:** 다양한 필터(카테고리, 상태, 위치) 및 정렬 옵션으로 사용자가 원하는 정보에 빠르게 접근하게 한다.
*   **데이터 정확성:** 중복 입출고 방지, 모순된 상태 전이 검증, 재고 수량의 자동 계산을 통해 데이터 무결성을 보장한다.

## 3. User Stories / Use Cases

*   **User Story 1: 재고 현황 조회**
    - **역할:** USER/MANAGER/ADMIN
    - **설명:** 사용자로서, 현재 보유 중인 전사 장비 목록을 조회하고 싶다. 그래서 어떤 장비가 재고에 있고 어느 위치에 있는지 파악할 수 있다.
    - *Acceptance Criteria:*
        - 재고 목록 페이지에서 모든 활성 장비가 테이블 형식으로 표시된다
        - 각 행에 장비 카테고리, 모델명, 시리얼 번호, 현재 위치, 상태가 표시된다
        - 기본 정렬: 카테고리 > 모델명 (오름차순)
        - 페이지네이션: 기본 20개 항목/페이지, 최대 100개 항목/페이지

*   **User Story 2: 필터링 및 검색**
    - **역할:** USER/MANAGER/ADMIN
    - **설명:** 사용자로서, 특정 카테고리(예: 모니터)의 장비만 필터링하거나 시리얼 번호로 검색하고 싶다. 그래서 원하는 장비를 빠르게 찾을 수 있다.
    - *Acceptance Criteria:*
        - 필터 조건: 카테고리(다중 선택), 상태(재고/출고/고장/폐기), 위치(자유 텍스트)
        - 검색: 시리얼 번호, 모델명 (부분 검색, 대소문자 무시)
        - 필터 적용 시 URL query parameter 업데이트
        - 필터 리셋: "초기화" 버튼으로 모든 필터 제거 + 기본값 복원

*   **User Story 3: 장비 상세 정보 조회**
    - **역할:** USER/MANAGER/ADMIN
    - **설명:** 사용자로서, 특정 장비의 상세 정보(구매일, 구매처, 현재 담당자, 이동 이력)를 확인하고 싶다. 그래서 장비의 전체 라이프사이클을 추적할 수 있다.
    - *Acceptance Criteria:*
        - 장비 상세 페이지: 기본 정보 + 이동 이력 타임라인 표시
        - 기본 정보: ID, 카테고리, 모델명, 시리얼 번호, 구매일, 구매처, 현재 상태, 현재 위치, 담당자
        - 이동 이력: 입고 → 위치 A → 위치 B → 출고 등의 순차적 기록
        - 각 이력 항목: 변경 유형, 이전 위치, 현재 위치, 담당자, 변경일시, 비고

*   **User Story 4: 입고 등록**
    - **역할:** MANAGER / ADMIN
    - **설명:** MANAGER/ADMIN으로서, 신규 장비를 시스템에 등록(입고)하고 싶다. 그래서 장비 취득부터 추적을 시작할 수 있다.
    - *Acceptance Criteria:*
        - 입고 폼: 카테고리(선택), 모델명, 시리얼 번호, 구매일, 구매처, 초기 위치, 비고(선택)
        - 필드 검증: 모든 필수 필드 입력 필수, 시리얼 번호 중복 체크
        - 제출 후: 상태 자동 설정 "재고", 입고 이력 자동 생성
        - 성공 메시지 + 상세 페이지로 자동 이동

*   **User Story 5: 출고 처리**
    - **역할:** MANAGER / ADMIN
    - **설명:** MANAGER/ADMIN으로서, 사용 중인 장비를 출고 처리하고 싶다. 그래서 언제 어디로 어떻게 사용되었는지 기록할 수 있다.
    - *Acceptance Criteria:*
        - 출고 폼: 장비 선택(상태: 재고인 것만), 출고 위치(자유 텍스트 또는 프로젝트명), 출고자, 예상 반납일(선택), 비고
        - 상태 변경: "재고" → "출고"
        - 이력 기록: 출고 타입 기록, 출고 위치, 출고자, 출고 일시 저장
        - 유효성 검증: 출고 가능 상태인지 확인

*   **User Story 6: 위치 변경 (보관 위치 이동)**
    - **역할:** MANAGER / ADMIN
    - **설명:** MANAGER/ADMIN으로서, 창고 정리 등의 이유로 장비의 위치를 변경하고 싶다. 그래서 장비의 현재 위치를 항상 정확하게 유지할 수 있다.
    - *Acceptance Criteria:*
        - 위치 변경 폼: 장비 선택, 새 위치(자유 텍스트), 사유(선택), 변경자
        - 조건: 상태가 "재고"인 장비만 위치 변경 가능
        - 이력 기록: 변경 타입, 이전 위치, 새 위치, 변경자, 변경 일시
        - 현재 위치 필드 즉시 업데이트

*   **User Story 7: 장비 상태 변경 (고장/폐기)**
    - **역할:** MANAGER / ADMIN
    - **설명:** MANAGER/ADMIN으로서, 고장 나거나 폐기 대상인 장비의 상태를 변경하고 싶다. 그래서 더 이상 사용 불가능한 장비가 실수로 출고되지 않도록 할 수 있다.
    - *Acceptance Criteria:*
        - 상태 변경 폼: 장비 선택, 새 상태(고장/폐기), 사유(필수), 변경자
        - 상태 전이 규칙:
            - 재고 → 고장 / 폐기 (O)
            - 출고 → 고장 / 폐기 (O, 반납 후)
            - 고장 → 폐기 (O)
            - 폐기 → 변경 불가 (최종 상태)
        - 이력 기록: 상태 변경 타입, 이유, 변경자, 변경 일시
        - 변경 후: 해당 장비는 출고 대상에서 제외

*   **User Story 8: 장비 반납**
    - **역할:** USER / MANAGER / ADMIN
    - **설명:** 사용자로서, 사용 중이던 장비를 반납하고 싶다. 그래서 장비를 다시 재고로 복귀시킬 수 있다.
    - *Acceptance Criteria:*
        - 반납 폼: 장비 선택(상태: 출고인 것만), 반납 위치, 반납자, 반납일
        - 상태 전이: "출고" → "재고"
        - 이력 기록: 반납 타입, 반납 위치, 반납자, 반납 일시
        - 현재 위치: 반납 위치로 업데이트

*   **User Story 9: 재고 통계**
    - **역할:** MANAGER / ADMIN
    - **설명:** MANAGER/ADMIN으로서, 카테고리별 재고 현황(총 수량, 재고 중, 출고 중, 고장 중)을 한눈에 보고 싶다. 그래서 전체 재고 상황을 빠르게 파악할 수 있다.
    - *Acceptance Criteria:*
        - 대시보드 또는 재고 목록 상단에 통계 패널 표시
        - 표시 항목: 카테고리별 총 수량, 재고 중, 출고 중, 고장 중, 폐기
        - 차트: 카테고리별 상태 분포 (Pie / Bar chart)
        - 갱신: 실시간 (데이터 변경 시 자동 갱신)

## 4. Scope

### 4.1 In-Scope

*   재고 목록 조회 (필터링, 정렬, 페이지네이션)
*   장비 상세 조회 (기본 정보 + 이동 이력)
*   입고 등록 (신규 장비 추가)
*   출고 처리 (장비 사용처 기록)
*   위치 변경 (보관 위치 이동)
*   반납 처리 (출고 → 재고)
*   상태 변경 (고장/폐기)
*   이력 관리 (모든 변경사항 기록)
*   재고 통계 (카테고리별, 상태별 집계)
*   권한 기반 접근 제어 (USER: 조회만, MANAGER: CRUD, ADMIN: 전체)
*   소프트 삭제 (deleted_at 컬럼)

### 4.2 Out-of-Scope

*   바코드 / QR코드 스캔 (2단계 구현)
*   자동 알림 (재고 부족 경보)
*   장비 예약 시스템
*   출고 승인 워크플로우
*   장비 성능 모니터링
*   외부 재고 시스템 연동 (ERP 통합)
*   자산 감가상각 계산
*   다국어 지원

## 5. Technical Considerations & Architecture Alignment

### 5.1 Next.js App Router Structure

*   **Page Routes:**
    - `src/app/(main)/inventory/page.tsx` — 재고 목록 페이지 (Server Component)
    - `src/app/(main)/inventory/[id]/page.tsx` — 장비 상세 페이지 (Server Component)
    - `src/app/(main)/inventory/new/page.tsx` — 입고 등록 페이지 (Server Component + Client Form)
    - `src/app/(main)/inventory/[id]/actions/page.tsx` — 출고/반납/위치변경/상태변경 페이지 (Server Component + Client Form)

*   **Layout:** `src/app/(main)/layout.tsx`에서 공통 레이아웃 상속

*   **Server vs Client Components:**
    - `inventory/page.tsx`: Server Component — 데이터 페칭, 권한 검증
    - `inventory/[id]/page.tsx`: Server Component — 장비 + 이력 조회
    - 폼 컴포넌트 (`InventoryForm`, `CheckoutForm` 등): Client Component — 폼 상태, 유효성 검증

### 5.2 API Route Handlers

*   `GET /api/inventory` — 재고 목록 조회 (필터, 정렬, 페이지네이션)
*   `POST /api/inventory` — 신규 장비 입고 등록
*   `GET /api/inventory/[id]` — 장비 상세 조회
*   `PUT /api/inventory/[id]` — 장비 기본 정보 수정 (ADMIN만)
*   `DELETE /api/inventory/[id]` — 소프트 삭제 (ADMIN만)
*   `POST /api/inventory/[id]/checkout` — 출고 처리
*   `POST /api/inventory/[id]/checkin` — 반납 처리
*   `POST /api/inventory/[id]/relocate` — 위치 변경
*   `POST /api/inventory/[id]/status` — 상태 변경
*   `GET /api/inventory/stats` — 재고 통계 (카테고리별 집계)

### 5.3 Database (Oracle XE 21c + TypeORM)

#### Entity 정의: `src/entities/Inventory.ts`

```
[Inventory]
├── id: number (PK)
├── category: string (VARCHAR2) — 카테고리 (예: 모니터, 노트북, 라우터 등)
├── model: string (VARCHAR2) — 모델명
├── serial_number: string (VARCHAR2, UNIQUE) — 시리얼 번호
├── purchase_date: Date — 구매일
├── purchase_from: string (VARCHAR2) — 구매처
├── current_location: string (VARCHAR2) — 현재 위치
├── current_status: string (VARCHAR2) — 상태 (재고/출고/고장/폐기)
├── notes: string (CLOB, nullable) — 비고
├── created_by_id: number (FK → Employee.id)
├── updated_by_id: number (FK → Employee.id)
├── created_at: DateTime — 생성일
├── updated_at: DateTime — 수정일
└── deleted_at: DateTime (nullable) — 소프트 삭제일
```

#### Entity 정의: `src/entities/InventoryHistory.ts`

```
[InventoryHistory]
├── id: number (PK)
├── inventory_id: number (FK → Inventory.id, ON DELETE RESTRICT)
├── change_type: string (VARCHAR2) — 변경 유형 (입고/출고/반납/위치변경/상태변경)
├── previous_location: string (VARCHAR2, nullable) — 이전 위치
├── new_location: string (VARCHAR2, nullable) — 새 위치
├── previous_status: string (VARCHAR2, nullable) — 이전 상태
├── new_status: string (VARCHAR2, nullable) — 새 상태
├── checkout_location: string (VARCHAR2, nullable) — 출고 위치 (출고 시만)
├── expected_checkin_date: Date (nullable) — 예상 반납일
├── reason: string (VARCHAR2, nullable) — 사유/비고
├── changed_by_id: number (FK → Employee.id)
├── changed_at: DateTime — 변경 일시
└── deleted_at: DateTime (nullable) — 소프트 삭제 (논리적으로는 사용 안 함)
```

#### Oracle 규칙 준수

*   VARCHAR2 사용 (VARCHAR 아님)
*   CLOB 사용 (TEXT 아님)
*   모든 FK: `ON DELETE RESTRICT`
*   `current_status` 제약: CHECK 또는 애플리케이션 검증 (재고/출고/고장/폐기)
*   `serial_number` UNIQUE 제약 (중복 입고 방지, deleted_at IS NULL 조건)
*   Soft delete 필수 (deleted_at 컬럼)

### 5.4 State Management

*   **Server State:** TanStack Query로 API 데이터 페칭/캐싱
    - `useInventoryList()` — 재고 목록, 필터 상태 관리
    - `useInventoryDetail()` — 장비 상세 + 이력
    - `useInventoryStats()` — 통계 데이터

*   **Client State:** Zustand 또는 React useState
    - 폼 입력 상태 (입고/출고/위치변경 폼)
    - 필터 선택값 (카테고리, 상태, 위치)
    - 페이지네이션 상태 (현재 페이지, 페이지 크기)

*   **Form State:** React Hook Form
    - 입고 폼, 출고 폼, 위치변경 폼, 상태변경 폼
    - 실시간 검증, 에러 메시지 표시

### 5.5 Authentication & Authorization

*   **NextAuth.js:** Session 기반 인증
*   **권한 검증:**
    - `USER`: 목록 조회, 상세 조회 읽기만 가능
    - `MANAGER`: 조회 + 입고/출고/반납/위치변경 가능
    - `ADMIN`: 모든 기능 (+ 수정/삭제)
*   **API Route:** 각 핸들러에서 `getServerSession()` → `user.role` 검증
*   **Page Route:** 클라이언트에서 `useSession()` 후 권한에 따라 UI 렌더링 (쓰기 버튼 숨김 등)
*   **Server Component:** 권한 검증 후 데이터만 전달, 폼 렌더링 제어

## 8. Security Considerations

*   **Authentication:** 모든 API route에서 `getServerSession()` 검증, 미인증 시 401 반환
*   **Authorization:** Role-based access control
    - USER: GET only
    - MANAGER: GET/POST/PUT (출고/반납 가능)
    - ADMIN: GET/POST/PUT/DELETE (모든 기능)
*   **Input Validation:** 서버사이드 필수
    - 카테고리: 허용값 리스트 확인
    - 시리얼 번호: 길이, 특수문자 검증
    - 날짜: 유효한 날짜 형식
*   **SQL Injection 방지:** TypeORM parameterized queries 사용
*   **XSS 방지:** React 자동 escaping, 사용자 입력은 항상 sanitize
*   **Data Protection:** 민감 정보 없음 (장비 정보는 공개 데이터)
*   **Soft Delete:** 물리 삭제 금지, `deleted_at` 필터로 논리 삭제

## 9. Open Questions & Dependencies

*   **Dependency 1:** Employee 엔티티의 역할(role) 정의 필수 (Phase 1에서 완료)
*   **Dependency 2:** 전체 레이아웃 구현 완료 필요 (2001_PRD 기반)
*   **Question 1:** 카테고리는 고정 리스트인가, 아니면 별도 테이블에서 관리할 것인가?
    - **결정:** 1단계는 고정 리스트 (하드코딩 또는 상수). 2단계에서 별도 테이블로 확장 고려.
*   **Question 2:** 예상 반납일 초과 시 자동 알림이 필요한가?
    - **결정:** Out-of-scope (2단계 구현)
*   **Question 3:** 출고 위치와 현재 위치는 동일한가?
    - **결정:** 논리적으로는 다름. 출고 위치 = 사용처 (프로젝트명 등), 현재 위치 = 물리 보관 위치. 이력에 모두 기록.
