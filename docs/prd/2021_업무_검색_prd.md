# Product Requirement Document: 업무 검색 (통합 조회)

**문서번호:** 2021
**작성일:** 2026-01-25
**상위문서:** 1000_초안.prd
**Phase:** 2 (Dashboard + Tasks)

---

## 1. Overview

본 PRD는 sunjin-erp 시스템의 "업무 검색 (통합 조회)" 기능에 대한 요구사항을 정의한다.
이 기능은 날짜(기간), 고객사명, 업무 유형, 직원별 복합 검색을 지원하여 등록된 업무를 테이블 형태로 조회하고, RBAC에 따라 조회 범위를 제어하는 통합 검색 페이지를 제공한다.

대시보드가 개인 캘린더 중심의 일정 관리 뷰라면, 업무 검색은 조건 기반 필터링과 데이터 테이블 뷰를 통한 다건 조회/분석에 초점을 맞춘다.

**대상 모듈:** 업무 검색
**대상 사용자 역할:** USER / MANAGER / ADMIN
**네비게이션 경로:** `/tasks`

---

## 2. Goals & Objectives

- **G1:** 날짜 범위, 고객사명, 업무 유형, 직원, 상태, 근무 형태를 조합한 복합 검색을 제공한다.
- **G2:** 검색 결과를 페이지네이션된 데이터 테이블로 표시하여 대량 데이터 조회를 지원한다.
- **G3:** RBAC에 따라 USER는 본인 업무만, MANAGER는 부서 내 업무, ADMIN은 전체 업무를 조회한다.
- **G4:** 검색 조건을 URL query param으로 유지하여 브라우저 히스토리/북마크/공유를 지원한다.
- **G5:** 검색 결과에서 개별 업무 상세 정보를 확인하고 수정할 수 있다.

## 3. User Stories / Use Cases

### US-1: 복합 조건 검색

**As a** USER, **I want to** 기간, 업무 유형, 상태 등 조건을 조합하여 업무를 검색하고 싶다, **so that** 특정 조건의 업무 이력을 빠르게 찾을 수 있다.

*Acceptance Criteria:*
- 검색 필터: 날짜 범위(시작~종료), 업무 유형, 근무 형태, 상태, 키워드(제목)
- 날짜 범위 기본값: 현재 월 1일 ~ 말일
- 필터 변경 시 URL query param 동기화 (브라우저 뒤로가기로 이전 검색 복원)
- 검색 버튼 클릭 또는 필터 변경 시 결과 갱신
- 초기화 버튼으로 모든 필터를 기본값으로 리셋

### US-2: 직원별 검색 (MANAGER/ADMIN)

**As a** MANAGER, **I want to** 부서 내 직원의 업무를 검색하고 싶다, **so that** 팀원의 업무 현황을 파악할 수 있다.

*Acceptance Criteria:*
- MANAGER: 직원 선택 드롭다운에 부서 내 직원 목록 표시
- ADMIN: 직원 선택 드롭다운에 전체 직원 목록 표시
- USER: 직원 선택 필터 미표시 (본인 업무만 조회)
- 직원 미선택 시: MANAGER는 부서 전체, ADMIN은 전체 직원 업무 조회

### US-3: 고객사별 검색

**As a** USER, **I want to** 고객사명으로 업무를 검색하고 싶다, **so that** 특정 고객 관련 업무 이력을 확인할 수 있다.

*Acceptance Criteria:*
- 고객사 검색 입력: 텍스트 입력 시 자동완성(autocomplete) 제공
- Customer 엔티티와 JOIN하여 고객사명으로 필터링
- 고객사가 지정되지 않은 업무도 결과에 포함 (필터 미적용 시)

### US-4: 검색 결과 테이블

**As a** USER, **I want to** 검색 결과를 테이블로 확인하고 싶다, **so that** 업무 내역을 일목요연하게 파악할 수 있다.

*Acceptance Criteria:*
- 테이블 컬럼: 날짜, 제목, 업무 유형, 근무 형태, 상태, 시간(시작~종료), 직원명(MANAGER/ADMIN), 고객사명
- 서버사이드 페이지네이션 (기본 20건/페이지, 10/20/50 선택 가능)
- 컬럼 헤더 클릭 시 정렬 (날짜, 제목, 상태)
- 결과 건수 표시 (예: "총 142건")
- 결과 없음 시 빈 상태 메시지 표시

### US-5: 업무 상세 조회/수정

**As a** USER, **I want to** 검색 결과에서 업무를 클릭하여 상세 정보를 확인하고 수정하고 싶다, **so that** 업무 내용을 갱신할 수 있다.

*Acceptance Criteria:*
- 테이블 행 클릭 시 상세 Dialog 또는 패널 표시
- 상세 화면에서 업무 정보 수정 가능 (제목, 설명, 상태, 시간 등)
- 수정 후 테이블 데이터 자동 갱신 (invalidateQueries)
- 본인 업무만 수정 가능 (타인 업무는 읽기 전용)

### US-6: 검색 결과 내보내기

**As a** MANAGER/ADMIN, **I want to** 검색 결과를 CSV로 내보내고 싶다, **so that** 보고서 작성에 활용할 수 있다.

*Acceptance Criteria:*
- 내보내기 버튼 클릭 시 현재 검색 조건 기준 전체 데이터 CSV 다운로드
- CSV 컬럼: 날짜, 제목, 업무 유형, 근무 형태, 상태, 시작시간, 종료시간, 직원명, 고객사명
- UTF-8 BOM 포함 (Excel 한글 호환)
- USER 역할은 내보내기 기능 미표시

## 5. Technical Considerations & Architecture Alignment

### 5.1 Next.js App Router Structure

- **Page Route:** `src/app/(main)/tasks/page.tsx` — 업무 검색 페이지 (기존 placeholder 교체)
- **Layout:** `src/app/(main)/layout.tsx` 공통 레이아웃 활용
- **Component Pattern:**
  - Page (Server Component): 초기 searchParams 전달
  - TaskSearchClient (Client Component): 필터 UI + 테이블 + 페이지네이션
  - TaskDetailDialog (Client Component): 상세 조회/수정 모달

### 5.2 API Route Handlers

기존 `GET /api/tasks` 확장 및 신규 엔드포인트 추가:

- `GET /api/tasks` — 목록 조회 (확장)
  - 추가 query params: `keyword`, `work_type`, `customer_id`, `page`, `page_size`, `sort_by`, `sort_order`
  - Response에 `total`, `page`, `page_size` 포함
  - RBAC 필터링: USER=본인, MANAGER=부서, ADMIN=전체
- `GET /api/tasks/[id]` — 상세 조회 (기존)
- `PUT /api/tasks/[id]` — 수정 (기존)
- `GET /api/tasks/export` — CSV 내보내기 (신규)
  - 현재 검색 조건 기반 전체 데이터 CSV 생성
  - MANAGER/ADMIN만 접근 가능
- `GET /api/customers/search` — 고객사 자동완성 (신규)
  - query param: `q` (검색어, 2자 이상)
  - Response: `{ customers: { id, name }[] }`

### 5.3 Database (Oracle XE 21c + TypeORM)

- **기존 Entity 활용:** `Task` 엔티티 (`src/entities/Task.ts`)
- **Customer Entity 필요:** 고객사 자동완성 및 JOIN을 위해 Customer 엔티티 선행 구현 필요
  - 미구현 시 고객사 필터는 `customer_id` 직접 입력으로 대체하거나 Phase 1 완료 후 활성화
- **Employee Entity 활용:** 직원 목록 드롭다운용 조회
- **Query 최적화:**
  - `IDX_TASK_EMPLOYEE_DATE` 인덱스 활용 (employee_id, task_date, deleted_at)
  - `IDX_TASK_DATE_EMPLOYEE` 인덱스 활용 (task_date, employee_id)
  - 페이지네이션: Oracle `OFFSET ... FETCH NEXT ... ROWS ONLY` 활용
  - keyword 검색: `task.title LIKE '%keyword%'` (Oracle 대소문자 구분 주의)

### 5.4 State Management

- **URL State (Single Source of Truth):** `useSearchParams()`로 검색 조건 관리
  - `date_from`, `date_to`, `type`, `work_type`, `status`, `keyword`, `employee_id`, `customer_id`
  - `page`, `page_size`, `sort_by`, `sort_order`
- **Server State:** TanStack Query로 검색 결과 fetching/caching
  - queryKey: `['tasks', 'search', { ...filterParams }]`
  - keepPreviousData: true (페이지 전환 시 깜빡임 방지)
- **Client State:** 없음 (모든 상태는 URL params 또는 TanStack Query)
- **Dialog State:** `useState`로 선택된 task ID 관리

### 5.5 Authentication & Authorization

- **Route Protection:** middleware.ts에서 인증 확인
- **API Level RBAC:**
  - USER: `task.employee_id = session.user.id`
  - MANAGER: `task.employee_id IN (부서 내 직원 ID 목록)` — Employee 엔티티의 department_id 기반
  - ADMIN: 필터 없음 (전체 조회)
- **수정 권한:** 본인 업무만 수정 가능 (`task.employee_id === session.user.id`)
- **내보내기 권한:** MANAGER/ADMIN만 `/api/tasks/export` 접근 가능

## 8. Security Considerations

- **Authentication:** 모든 API route에서 NextAuth session 확인
- **Authorization:**
  - API level에서 RBAC 강제 적용 (클라이언트 필터링에만 의존하지 않음)
  - 수정 API에서 `task.employee_id === session.user.id` 검증
  - 내보내기 API에서 MANAGER/ADMIN role 검증
- **Input Validation:**
  - 날짜 파라미터 형식 검증 (ISO date string)
  - keyword 파라미터 SQL injection 방지 (parameterized query)
  - page/page_size 숫자 범위 검증 (page_size max 100)
  - customer_id, employee_id 숫자 타입 검증
- **Data Protection:**
  - CSV 내보내기 시 민감 정보 제외 (비밀번호 등)
  - 대량 데이터 조회 시 rate limiting 고려 (향후)

## 9. Open Questions & Dependencies

- **Q1:** Customer 엔티티가 아직 미구현 상태. 고객사 검색 기능은 Customer 모듈 (Phase 1) 완료 후 활성화하는 것이 적절한가?
  - 대안: customer_id만으로 필터링하고, 고객사명 표시는 Phase 1 완료 후 JOIN 추가
- **Q2:** MANAGER의 "부서 내 직원" 조회 범위를 위해 Employee 엔티티의 department_id 기반 쿼리가 필요. Phase 1 Employee 모듈 선행 필요.
  - 대안: Phase 2에서는 MANAGER도 본인 업무만 조회, Phase 1 완료 후 부서 범위 확장
- **Q3:** keyword 검색에서 Oracle LIKE 검색의 성능 이슈 가능. 대량 데이터 시 Full-Text Index 도입 검토 필요한가?
- **Dependency 1:** Employee 엔티티 및 department_id 필드 (Phase 1)
- **Dependency 2:** Customer 엔티티 (Phase 1) — 고객사 자동완성 및 JOIN
- **Dependency 3:** 대시보드 Task API 기본 구현 완료 (2011 PRD) — 이미 완료

## 10. Implementation Strategy

### Phase 2-A (즉시 구현 가능)

Customer/Employee 모듈 미완성 상태에서도 구현 가능한 범위:
- 검색 필터 UI (날짜, 유형, 형태, 상태, 키워드)
- 데이터 테이블 (페이지네이션, 정렬)
- URL query param 상태 관리
- 업무 상세 Dialog (조회/수정)
- USER: 본인 업무만 조회
- MANAGER/ADMIN: 전체 조회 (부서 필터링은 Phase 1 완료 후)
- 직원 선택 드롭다운: 미표시 (Phase 1 완료 후 활성화)
- 고객사 검색: 미표시 (Phase 1 완료 후 활성화)

### Phase 2-B (Phase 1 완료 후)

- 직원 선택 드롭다운 활성화 (Employee 엔티티 기반)
- MANAGER 부서 범위 필터링
