## CP-1: 첨부파일 단일 제한 [HIGH]

**비평 타당성: 인정**

프로젝트 특성상 복수 파일(계약서, 제안서, 견적서 등)이 필요한 것은 타당한 지적. 기술지원 모듈의 단일 파일 패턴을 그대로 따르는 것은 프로젝트의 업무 특성과 맞지 않음.

**반박:**
- 초기 구현 복잡도를 고려하면 단일 파일로 시작하여 안정화 후 확장하는 것도 방법
- 그러나 DB 스키마는 초기에 올바르게 설계하는 것이 마이그레이션 비용 절감

**결론:** 별도 PROJECT_ATTACHMENT 테이블로 1:N 설계 채택 권장. 초기 UI는 간단하게, 스키마는 확장 가능하게.

## CP-2: 프로젝트 코드 생성 동시성 이슈 [HIGH]

**비평 타당성: 부분 인정**

동시성 문제는 이론적으로 존재하나, 실제 사용 환경(소수 사용자, 프로젝트 등록 빈도 낮음)에서 발생 확률은 매우 낮음.

**반박:**
- 선진인포텍 규모에서 동일 초 내 복수 프로젝트 생성 확률은 극히 낮음
- 그럼에도 Oracle SEQUENCE 활용이 간단하고 안전한 해결책

**결론:** Oracle SEQUENCE(`PROJECT_CODE_SEQ`) 활용하여 NNN 부분 생성. 구현 비용 미미하면서 동시성 안전 보장.

## CP-3: 상태와 체크리스트 연동 규칙 불명확 [HIGH]

**비평 타당성: 인정**

엣지케이스 규칙이 명확히 정의되지 않아 구현 시 혼란 가능.

**반박:**
- 상태와 체크리스트를 독립적으로 관리하는 것이 실제 업무 유연성에 부합
- "모든 체크 완료 시 COMPLETED 제안"은 편의 기능으로, 강제가 아님

**결론:** 다음 규칙 명시 필요:
1. 체크리스트 변경은 상태에 자동 영향 없음 (독립적)
2. 모든 체크 완료 시 "상태를 완료로 변경하시겠습니까?" 알림만 표시 (거절 가능)
3. COMPLETED 상태에서도 체크리스트 수정 가능 (상태 자동 변경 없음)
4. 어떤 상태에서든 체크리스트 체크/해제 가능

## CP-5: 계약 금액 접근 권한 [MEDIUM]

**비평 타당성: 부분 인정**

현재 구조에서 USER는 본인 담당 건만 조회하므로 실질적 보안 이슈 없음. 그러나 명시적 정책이 문서에 있는 것이 좋음.

**반박:**
- USER가 본인 건의 금액을 아는 것은 업무상 필요 (영업 담당자가 자기 프로젝트 금액을 모르면 안 됨)
- 컬럼 레벨 접근 제어는 과도한 복잡도 추가

**결론:** 현재 구조 유지. "USER는 본인 담당 프로젝트의 계약 금액을 조회할 수 있다"로 명시하여 의도적 설계임을 문서화.

## CP-8: 체크리스트 비순차적 체크의 비즈니스 타당성 [LOW]

**비평 타당성: 부분 인정**

논리적 순서 무시가 가능하면 데이터 품질 저하 우려 있으나, 실제 영업에서는 비순차적 진행이 빈번함.

**반박:**
- 실제 업무: 견적 먼저 제출 후 회의, 또는 계약 후 제안서 보완 등 비순차 진행 흔함
- 순차 강제 시 사용자가 시스템 우회(허위 체크)할 가능성 높음
- 유연성이 사용자 만족도와 데이터 정확성에 더 기여

**결론:** 비순차적 체크 허용 유지. 단, 이전 단계 미완료 시 시각적 표시(미완료 항목 하이라이트)로 인지 유도.

## CP-9: project_code NULL 허용과 UNIQUE 조합 [LOW]

**비평 타당성: 부분 인정**

Oracle에서 NULL + UNIQUE는 기술적으로 문제없으나 설계 의도가 모호.

**반박:**
- 초기 영업 상담 단계에서는 공식 프로젝트 코드가 불필요 (잠재 고객 관리)
- 계약 확정 후 코드 생성이 업무 프로세스에 자연스러움
- 모든 프로젝트에 코드를 강제하면 "PJT-20260125-TBD" 같은 무의미한 코드 생성 유발

**결론:** NULL 허용 유지. PRD에 "초기 영업 단계에서는 코드 미부여, 계약 진행 시 코드 생성"이라는 업무 규칙 명시.

## CP-10: 수정 API의 체크리스트 업데이트 방식 [LOW]

**비평 타당성: 인정**

체크리스트 토글에 전체 PUT을 사용하면 비효율적이고 동시 수정 충돌 가능.

**반박:**
- 프로젝트 수정 빈도가 낮아 동시 충돌 확률 극히 낮음
- 그러나 UX 관점에서 체크리스트 토글은 빈번한 인터랙션이므로 별도 API가 합리적

**결론:** `PATCH /api/projects/[id]/checklist` 추가. Body: `{ stage: string, completed: boolean }`. 기본 정보 수정(`PUT`)과 체크리스트 토글(`PATCH`)을 분리.
