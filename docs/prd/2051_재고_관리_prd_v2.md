## 1. Overview

본 PRD는 sunjin-erp 시스템의 "재고 관리" 기능에 대한 요구사항을 정의한다.
이 기능은 회사 내 IT 장비(모니터, 네트워크 장비, 소프트웨어 등)의 입출고 현황을 추적하고, 각 장비의 위치와 이동 이력을 관리하는 통합 인벤토리 시스템을 구축한다.

**대상 모듈:** 재고 관리 (Inventory Management)
**대상 사용자 역할:** USER (조회만) / MANAGER (CRUD) / ADMIN (전체)
**주요 기능:** 장비 카테고리별 조회, 시리얼 번호 기반 추적, 위치 관리, 입출고 이력

## 2. Goals & Objectives

*   **장비 인벤토리 시각화:** 전사 장비의 현황을 카테고리, 모델명, 시리얼 번호 기반으로 조회하여 재고 파악의 정확성을 높인다.
*   **위치 추적:** 각 장비의 보관 위치 및 출고 위치를 실시간으로 관리하여 필요 시 신속한 장비 검색을 가능하게 한다.
*   **이력 관리:** 장비 입고, 출고, 이동 내역을 시간순으로 기록하여 추후 감사(audit) 및 사용처 추적을 지원한다.
*   **효율적인 조회:** 다양한 필터(카테고리, 상태, 위치) 및 정렬 옵션으로 사용자가 원하는 정보에 빠르게 접근하게 한다.
*   **데이터 정확성:** 중복 입출고 방지, 모순된 상태 전이 검증, 재고 수량의 자동 계산을 통해 데이터 무결성을 보장한다.

## 3. User Stories / Use Cases

*   **User Story 1: 재고 현황 조회**
    - **역할:** USER/MANAGER/ADMIN
    - **설명:** 사용자로서, 현재 보유 중인 전사 장비 목록을 조회하고 싶다. 그래서 어떤 장비가 재고에 있고 어느 위치에 있는지 파악할 수 있다.
    - *Acceptance Criteria:*
        - 재고 목록 페이지에서 모든 활성 장비가 테이블 형식으로 표시된다
        - 각 행에 장비 카테고리, 모델명, 시리얼 번호, 현재 위치, 상태가 표시된다
        - 기본 정렬: 카테고리 > 모델명 (오름차순)
        - 페이지네이션: 기본 20개 항목/페이지, 최대 100개 항목/페이지

*   **User Story 2: 필터링 및 검색**
    - **역할:** USER/MANAGER/ADMIN
    - **설명:** 사용자로서, 특정 카테고리(예: 모니터)의 장비만 필터링하거나 시리얼 번호로 검색하고 싶다. 그래서 원하는 장비를 빠르게 찾을 수 있다.
    - *Acceptance Criteria:*
        - 필터 조건: 카테고리(다중 선택), 상태(재고/출고/고장/폐기), 위치(자유 텍스트)
        - 검색: 시리얼 번호, 모델명 (접두사 검색, 대소문자 무시) — Phase 1은 접두사 기반, Phase 2에서 전문검색 지원
        - 필터 적용 시 URL query parameter 업데이트
        - 필터 리셋: "초기화" 버튼으로 모든 필터 제거 + 기본값 복원

*   **User Story 3: 장비 상세 정보 조회**
    - **역할:** USER/MANAGER/ADMIN
    - **설명:** 사용자로서, 특정 장비의 상세 정보(구매일, 구매처, 현재 담당자, 이동 이력)를 확인하고 싶다. 그래서 장비의 전체 라이프사이클을 추적할 수 있다.
    - *Acceptance Criteria:*
        - 장비 상세 페이지: 기본 정보 + 이동 이력 타임라인 표시
        - 기본 정보: ID, 카테고리, 모델명, 시리얼 번호, 구매일, 구매처, 현재 상태, 현재 위치, 담당자
        - 이동 이력: 입고 → 위치 A → 위치 B → 출고 등의 순차적 기록
        - 각 이력 항목: 변경 유형, 이전 위치, 현재 위치, 담당자, 변경일시, 비고
        - 과기 판정: 기대 반납일이 지나고 상태가 '출고'인 경우 "과기 (N일)" 표시

*   **User Story 4: 입고 등록**
    - **역할:** MANAGER / ADMIN
    - **설명:** MANAGER/ADMIN으로서, 신규 장비를 시스템에 등록(입고)하고 싶다. 그래서 장비 취득부터 추적을 시작할 수 있다.
    - *Acceptance Criteria:*
        - 입고 폼: 카테고리(선택), 모델명, 시리얼 번호, 구매일, 구매처, 초기 위치, 비고(선택)
        - 필드 검증: 모든 필수 필드 입력 필수, 시리얼 번호 중복 체크
        - 제출 후: 상태 자동 설정 "재고", 입고 이력 자동 생성
        - 성공 메시지 + 상세 페이지로 자동 이동

*   **User Story 5: 출고 처리**
    - **역할:** MANAGER / ADMIN
    - **설명:** MANAGER/ADMIN으로서, 사용 중인 장비를 출고 처리하고 싶다. 그래서 언제 어디로 어떻게 사용되었는지 기록할 수 있다.
    - *Acceptance Criteria:*
        - 출고 폼: 장비 선택(상태: 재고인 것만), 출고 위치(자유 텍스트 또는 프로젝트명), 출고자, 예상 반납일(선택), 비고
        - 상태 변경: "재고" → "출고"
        - 이력 기록: 출고 타입 기록, 출고 위치, 출고자, 출고 일시 저장
        - 유효성 검증: 출고 가능 상태인지 확인 (상태 = "재고"만 허용)

*   **User Story 6: 위치 변경 (보관 위치 이동)**
    - **역할:** MANAGER / ADMIN
    - **설명:** MANAGER/ADMIN으로서, 창고 정리 등의 이유로 장비의 위치를 변경하고 싶다. 그래서 장비의 현재 위치를 항상 정확하게 유지할 수 있다.
    - *Acceptance Criteria:*
        - 위치 변경 폼: 장비 선택, 새 위치(자유 텍스트), 사유(선택), 변경자
        - 조건: 상태가 "재고"인 장비만 위치 변경 가능
        - 이력 기록: 변경 타입, 이전 위치, 새 위치, 변경자, 변경 일시
        - 현재 위치 필드 즉시 업데이트

*   **User Story 7: 장비 상태 변경 (고장/폐기)**
    - **역할:** MANAGER / ADMIN
    - **설명:** MANAGER/ADMIN으로서, 고장 나거나 폐기 대상인 장비의 상태를 변경하고 싶다. 그래서 더 이상 사용 불가능한 장비가 실수로 출고되지 않도록 할 수 있다.
    - *Acceptance Criteria:*
        - 상태 변경 폼: 장비 선택, 새 상태(고장/폐기), 사유(필수), 변경자
        - 상태 전이 규칙: (자세히는 Section 3.1 참조)
            - 재고 → 고장 / 폐기 (O)
            - 출고 → 고장 (O, 현재 상태) / 폐기 (X, 반납 후에만 가능)
            - 고장 → 폐기 (O)
            - 폐기 → 변경 불가 (최종 상태)
        - 이력 기록: 상태 변경 타입, 이유, 변경자, 변경 일시
        - 변경 후: 해당 장비는 출고 대상에서 제외

*   **User Story 8: 장비 반납**
    - **역할:** MANAGER / ADMIN (변경됨, v1에서는 USER/MANAGER/ADMIN)
    - **설명:** MANAGER/ADMIN으로서, 사용 중이던 장비를 반납하고 싶다. 그래서 장비를 다시 재고로 복귀시킬 수 있다.
    - *Acceptance Criteria:*
        - 반납 폼: 장비 선택(상태: 출고인 것만), 반납 위치, 반납자, 반납일
        - 상태 전이: "출고" → "재고"
        - 이력 기록: 반납 타입, 반납 위치, 반납자, 반납 일시
        - 현재 위치: 반납 위치로 업데이트

*   **User Story 9: 재고 통계**
    - **역할:** MANAGER / ADMIN
    - **설명:** MANAGER/ADMIN으로서, 카테고리별 재고 현황(총 수량, 재고 중, 출고 중, 고장 중)을 한눈에 보고 싶다. 그래서 전체 재고 상황을 빠르게 파악할 수 있다.
    - *Acceptance Criteria:*
        - 대시보드 또는 재고 목록 상단에 통계 패널 표시
        - 표시 항목: 카테고리별 총 수량, 재고 중, 출고 중, 고장 중, 폐기
        - 차트: 카테고리별 상태 분포 (Pie / Bar chart)
        - 갱신: 근실시간 (사용자 작업 후 데이터 변경 시 자동 갱신, <200ms 지연)

### 3.1 상태 전이 다이어그램

```
[재고 (In Stock)]
├─→ [출고 (Checked Out)] ──→ [재고] (반납 시)
│                       └──→ [고장] (사용 중 고장 시)
├─→ [고장 (Broken)] ──→ [폐기] (유일한 경로)
└─→ [폐기 (Deprecated)] ──→ FINAL (변경 불가)

핵심 규칙:
1. 출고 상태에서는 폐기로 직접 변경 불가 (반납 후에만 가능)
2. 고장 상태는 폐기로만 변경 가능 (수리 불가)
3. 폐기는 최종 상태 (변경 불가)
4. 위치 변경은 재고 상태에서만 가능
```

### 3.2 위치 관리 의미론

**두 가지 위치 개념:**

| 필드 | 설명 | 언제 업데이트 | 비고 |
|------|------|------------|------|
| current_location | 물리적 보관 위치 (창고/사무실) | 입고, 위치변경, 반납 | Inventory 엔티티의 필드 |
| checkout_location | 논리적 사용처 (프로젝트, 사람) | 출고 시만 | InventoryHistory에만 기록 |

**각 작업별 위치 업데이트:**

| 작업 | current_location | checkout_location | 설명 |
|------|-----------------|------------------|------|
| 입고 | 사용자가 지정 | N/A | 입고 시 현재 위치 설정 |
| 출고 | 변경 없음 | 사용처 기록 | 물리 위치는 창고, 논리적 사용처 기록 |
| 위치변경 | 새 위치로 업데이트 | N/A | 재고 상태에서만 가능 |
| 반납 | 반납 위치로 업데이트 | 초기화 | 사용자가 반납 위치 지정 |

## 4. Scope

### 4.1 In-Scope

*   재고 목록 조회 (필터링, 정렬, 페이지네이션)
*   장비 상세 조회 (기본 정보 + 이동 이력 + 과기 판정)
*   입고 등록 (신규 장비 추가)
*   출고 처리 (장비 사용처 기록)
*   위치 변경 (보관 위치 이동)
*   반납 처리 (출고 → 재고)
*   상태 변경 (고장/폐기) — 즉시 (승인 없음)
*   이력 관리 (모든 변경사항 기록, 불변)
*   재고 통계 (카테고리별, 상태별 집계) — 근실시간
*   권한 기반 접근 제어 (USER: 조회만, MANAGER: CRUD, ADMIN: 전체)
*   소프트 삭제 (deleted_at 컬럼)
*   시리얼 번호 중복 검증 (부분 고유 인덱스 + 애플리케이션 검증)
*   접두사 기반 검색 (Phase 1, 성능 최적화용)

### 4.2 Out-of-Scope

*   바코드 / QR코드 스캔 (2단계 구현)
*   자동 알림 (재고 부족 경보, 과기 장비 알림) — Phase 2
*   장비 예약 시스템
*   출고 / 상태변경 승인 워크플로우 — Phase 2에서 고가 장비(>$5000) 승인 추가 예정
*   장비 성능 모니터링
*   외부 재고 시스템 연동 (ERP 통합)
*   자산 감가상각 계산
*   다국어 지원
*   전문검색 (full-text search) — Phase 2
*   부서별 권한 스코핑 — Phase 2
*   장비 담당자 추적 (assigned_to_id) — Phase 2

## 5. Technical Considerations & Architecture Alignment

### 5.1 Next.js App Router Structure

*   **Page Routes:**
    - `src/app/(main)/inventory/page.tsx` — 재고 목록 페이지 (Server Component, Client Component 호출)
    - `src/app/(main)/inventory/[id]/page.tsx` — 장비 상세 페이지 (Server Component, Client Component 호출)
    - `src/app/(main)/inventory/new/page.tsx` — 입고 등록 페이지 (Server Component, Client Form)
    - `src/app/(main)/inventory/loading.tsx` — 로딩 스켈레톤

*   **Layout:** `src/app/(main)/layout.tsx`에서 공통 레이아웃 상속

*   **Server vs Client Components (sunjin-erp 패턴):**
    - Page Route (Server Component): `getServerSession()` 호출로 인증 검증만 수행
    - Client Component: TanStack Query를 통해 API에서 데이터 페칭
    - 폼 컴포넌트: Client Component — 폼 상태, 유효성 검증, mutation 호출

**올바른 패턴:**
```typescript
// app/(main)/inventory/page.tsx (Server Component)
export default async function InventoryPage() {
  const session = await getServerSession(); // ✓ Auth check only
  if (!session) redirect('/login');
  return <InventoryListClient />;  // ✓ Render client component
}

// components/features/inventory/InventoryListClient.tsx (Client Component)
export function InventoryListClient() {
  const { data, isLoading } = useInventoryList(); // ✓ TanStack Query
  return <InventoryTable data={data} />;
}
```

### 5.2 API Route Handlers

**기본 CRUD 엔드포인트:**

*   `GET /api/inventory` — 재고 목록 조회 (필터, 정렬, 페이지네이션)
*   `POST /api/inventory` — 신규 장비 입고 등록
*   `GET /api/inventory/[id]` — 장비 상세 조회 (과기 판정 포함)
*   `PUT /api/inventory/[id]` — 장비 기본 정보 수정 (ADMIN만)
*   `DELETE /api/inventory/[id]` — 소프트 삭제 (ADMIN만)

**작업 엔드포인트:**

*   `POST /api/inventory/[id]/checkout` — 출고 처리
*   `POST /api/inventory/[id]/checkin` — 반납 처리
*   `POST /api/inventory/[id]/relocate` — 위치 변경
*   `POST /api/inventory/[id]/status` — 상태 변경

**조회 엔드포인트:**

*   `GET /api/inventory/stats` — 재고 통계 (카테고리별 집계)

#### 5.2.1 Query Parameters

**GET /api/inventory**

```
Query Parameters:
- page: number (기본값 1, 최소값 1)
- pageSize: number (기본값 20, 최소값 1, 최대값 100)
  → pageSize > 100인 경우 400 에러 반환: "Page size cannot exceed 100"
- categories: string[] (쉼표 구분 또는 반복)
  예: ?categories=monitor,keyboard 또는 ?categories=monitor&categories=keyboard
- status: string[] (쉼표 구분, 값: 재고, 출고, 고장, 폐기)
  예: ?status=재고,출고
```

#### Oracle 규칙 준수

*   VARCHAR2 사용 (VARCHAR 아님)
*   CLOB 사용 (TEXT 아님)
*   모든 FK: `ON DELETE RESTRICT`
*   `current_status` 제약: CHECK 제약 + 애플리케이션 검증 (재고/출고/고장/폐기)
*   `serial_number` 부분 고유 인덱스 (중복 입고 방지, deleted_at IS NULL 조건) — Oracle 12c+
*   Soft delete 필수 (deleted_at 컬럼)
*   InventoryHistory는 deleted_at 컬럼 없음 (불변 audit trail)

#### 부분 고유 인덱스 구현

**문제:** Oracle은 조건부 UNIQUE 제약을 지원하지 않음. 소프트 삭제된 레코드는 시리얼번호 재사용 가능해야 함.

**해결책 (Decision 5):**

1. **데이터베이스 레벨 (Primary):**
   ```sql
   CREATE UNIQUE INDEX idx_inventory_serial_active
   ON inventory(serial_number) WHERE deleted_at IS NULL;
   ```
   - Oracle XE 21c에서 지원
   - ORA-00001 오류로 중복 방지

2. **애플리케이션 레벨 (Secondary, UX 개선):**
   ```typescript
   @ValidateSerialUnique() // DTO에 custom validator
   serial_number: string;
   ```
   - DB 라운드트립 전에 검증
   - 사용자 친화적 에러 메시지

#### Soft Delete 정책 (Decision 6)

**Inventory (부모):**
- Soft delete 지원: `UPDATE inventory SET deleted_at = NOW()`
- GET /api/inventory에서 제외
- GET /api/inventory/[id]는 ADMIN만 접근 가능 (deleted 기록 조회)

**InventoryHistory (자식):**
- Soft delete **하지 않음** (불변 audit trail)
- `deleted_at` 컬럼 **없음**
- 부모 deleted 후에도 조회 가능
- 감사(audit) 목적으로 영구 보존

#### 5.4.1 Cache Invalidation Strategy (Decision 7)

**각 작업 후 무효화할 쿼리:**

| 작업 | inventory-list | inventory-detail | inventory-stats | 사유 |
|------|-----------------|------------------|-----------------|------|
| 입고 등록 | ✓ Yes | — | ✓ Yes | 새 항목 추가, 통계 변경 |
| 정보 수정 | ✓ Yes | ✓ Yes | ✓ 조건부 | 항목 수정 |
| 출고 | ✓ Yes | ✓ Yes | ✓ Yes | 상태 변경, 통계 변경 |
| 반납 | ✓ Yes | ✓ Yes | ✓ Yes | 상태 변경, 통계 변경 |
| 위치변경 | ✓ Yes | ✓ Yes | ✗ No | 위치 변경만, 상태는 같음 |
| 상태변경 | ✓ Yes | ✓ Yes | ✓ Yes | 상태 변경, 통계 변경 |
| 소프트 삭제 | ✓ Yes | ✗ No | ✓ Yes | 목록에서 제외, 통계 변경 |

**구현 패턴:**

```typescript
// hooks/useInventoryMutations.ts
export function useInventoryMutations() {
  const queryClient = useQueryClient();

  const invalidateDetail = (id: number) => {
    queryClient.invalidateQueries(['inventory-detail', id]);
  };

  const invalidateListAndStats = () => {
    queryClient.invalidateQueries(['inventory-list']);
    queryClient.invalidateQueries(['inventory-stats']);
  };

  return {
    createMutation: useMutation(createInventory, {
      onSuccess: () => invalidateListAndStats()
    }),

    checkoutMutation: useMutation(checkoutInventory, {
      onSuccess: (data) => {
        invalidateDetail(data.id);
        invalidateListAndStats();
      }
    }),

    relocateMutation: useMutation(relocateInventory, {
      onSuccess: (data) => {
        invalidateDetail(data.id);
        queryClient.invalidateQueries(['inventory-list']); // Location changed only
        // Stats NOT invalidated (status unchanged)
      }
    })
  };
}
```

### 8.4 SQL Injection Prevention

*   TypeORM parameterized queries 사용 (기본값)
*   QueryBuilder로 모든 검색 수행 (raw query 금지)

```typescript
// CORRECT
const inventory = await repository
  .createQueryBuilder('i')
  .where('i.model LIKE :search', { search: `${searchTerm}%` })
  .getMany();

// WRONG (never do this)
const inventory = await repository.query(
  `SELECT * FROM inventory WHERE model LIKE '%${searchTerm}%'`
);
```

*   Custom repository 또는 query builder 사용

```typescript
// CORRECT
const active = await repository.find({

});

// WRONG
const all = await repository.find(); // Can include deleted!
```
