# Product Requirement Document (v2): 장애 현황 관리 (Issue Tracking)

문서번호: 2051
작성일: 2026-01-25
버전: v2 (토론 주제 해결 및 중재 결정 반영)
상위문서: 1000_초안.prd, 2001_전체_레이아웃_설정_prd_v2.md

## 1. Overview

본 PRD는 sunjin-erp 시스템의 "장애 현황 관리" 기능에 대한 요구사항을 정의한다.
이 기능은 고객사에서 발생한 IT 장애(Issues)를 접수받아 처리하고, 처리 방법, 담당자, 결과를 통합적으로 관리하는 모듈이다.
영업/기술지원팀은 장애 발생부터 완료까지의 전체 라이프사이클을 추적하고, 고객사별 장애 현황을 대시보드 형태로 파악할 수 있다.

**대상 모듈:** 장애 현황 관리 (Issue Tracking)
**대상 사용자 역할:** ADMIN (전체 권한), MANAGER (부서 및 담당 고객사 제한), USER (조회/등록만)

## 2. Goals & Objectives

* **장애 접수 및 추적:** 고객사별 장애 내역을 중앙에서 등록하고, 접수 상태(진행중/완료)를 실시간 추적한다.
* **효율적인 할당 및 처리:** 담당자 배정, 처리 방법(원격/전화/현장) 선택, 완료 리포트 작성까지 일관된 워크플로우를 제공한다.
* **고객 만족도 제고:** 장애 처리 이력 투명성, 빠른 대응 시간 측정, 결과 리포트 첨부로 신뢰도 증대.
* **데이터 기반 분석:** 장애 유형별/고객사별 통계, 처리 시간 분석을 통해 운영 효율성 개선.
* **RBAC 준수:** 직원별 역할에 따른 접근 제한 (ADMIN 전체 열람, MANAGER 부서내 제한, USER 제한적 조회).

## 3. User Stories / Use Cases

* **US-1 (장애 접수):** 기술지원팀 USER로서, 신규 장애를 빠르게 등록할 수 있다. 그래서 고객 요청에 신속히 대응할 수 있다.
    * *Acceptance Criteria:*
        * 고객사 선택 → 장애 제목 입력 → 심각도(심각/중요/보통/낮음) 선택 → 상세 설명 입력 후 저장
        * 장애 등록 후 자동으로 상태는 "접수"로 설정, 생성자(등록자)가 자동 기록됨
        * 담당자 미지정 상태에서도 등록 가능 (나중에 할당 가능)
        * **등록 시 공개 여부는 기본값 "비공개(is_public=false)"로 설정 (보안 우선)**
        * 등록 완료 후 토스트 알림 표시, 상세 페이지로 이동

* **US-2 (담당자 할당):** MANAGER 역할로서, 부서 내 장애를 담당자에게 할당할 수 있다. 그래서 적절한 인원이 담당하게 된다.
    * *Acceptance Criteria:*
        * 상세 페이지에서 담당자 드롭다운을 통해 사원 선택 가능
        * **부서 내 사원만 표시 (해당 부서의 직원 리스트만) — MANAGER는 다른 부서 직원 할당 불가**
        * 할당 후 변경 이력 기록 (담당자 변경 시 변경 로그 남음)
        * ADMIN은 모든 직원에게 할당 가능

* **US-3 (처리 방법 기록):** 담당자로서, 장애를 처리한 방법(원격/전화/현장)을 선택하고 처리 결과를 입력할 수 있다.
    * *Acceptance Criteria:*
        * 처리 방법 라디오 버튼: 원격 지원, 전화 지원, 현장 방문 중 선택
        * **처리 시간(소요 시간) 입력 필드: 분 단위 단일 입력 (1~1440분)**
        * **실시간 포맷팅: 150분 입력 시 "약 2시간 30분" 표시**
        * **표시: 상세 페이지와 목록에서 "2시간 30분" 형식으로 포맷팅**
        * 처리 결과 텍스트 입력: 해결 방법, 원인, 추가 조치 사항 등

* **US-4 (완료 리포트 첨부):** 담당자로서, 완료 리포트 파일을 첨부하고 상태를 "완료"로 변경할 수 있다.
    * *Acceptance Criteria:*
        * 파일 업로드 (1개 이상, 최대 5개, 각 10MB 제한)
        * 파일 유형: PDF, Excel, Word, 이미지 등 일반 문서 포맷만 허용
        * **파일 검증: 프론트엔드에서 실시간 피드백 + 서버에서 재검증**
        * **Issue 삭제 전 첨부파일 제거 필수 (ON DELETE RESTRICT 정책)**
        * 첨부 후 파일 리스트 표시 (다운로드, 삭제 가능)
        * 완료 버튼 클릭 → 상태 "완료" 저장, 완료일시 자동 기록

* **US-5 (장애 목록 조회):** USER로서, 고객사별/상태별로 장애를 조회하고 현황을 파악할 수 있다.
    * *Acceptance Criteria:*
        * **권한별 조회 범위:**
          - **ADMIN: 모든 Issue 조회 가능**
          - **MANAGER: 같은 부서 Issue만 조회 (해당 부서의 담당자가 배정된 Issue)**
          - **USER: 자신이 생성/담당한 Issue + 같은 부서의 공개(is_public=true) Issue**
        * 필터: 고객사, 상태(접수/진행중/완료), 심각도, 담당자, 날짜 범위 (복합 필터 지원)
        * **필터 조합: AND 연결 (모든 필터 동시 적용)**
        * 정렬: 생성일(기본 내림차순), 심각도, 담당자 등
        * 페이지네이션: 기본 20개 per page, 최대 100개
        * 각 행 클릭 시 상세 페이지로 이동

* **US-6 (대시보드 현황):** MANAGER로서, 부서별 장애 통계(접수/진행중/완료 카운트)를 한눈에 볼 수 있다.
    * *Acceptance Criteria:*
        * 요약 배지: "전체 0건 | 진행중 0건 | 완료 0건"
        * **필터(고객사, 심각도 등) 변경 시 배지 수 동적 업데이트**
        * **배지 클릭 = 현재 필터 + 상태 필터 (AND 조합)**
        * 클릭 가능한 배지: 해당 필터 상태로 목록 포커싱

* **US-7 (상세 정보 조회):** USER로서, 특정 장애의 전체 정보(접수자, 담당자, 처리 방법, 완료 리포트 등)를 조회할 수 있다.
    * *Acceptance Criteria:*
        * 기본 정보 섹션: 제목, 고객사, 심각도, 상태, 생성일, 담당자
        * **공개 여부 토글: 이 Issue를 같은 부서원이 조회 가능하도록 설정 (MANAGER/ADMIN만 수정 가능)**
        * 처리 정보 섹션: 처리 방법, 소요 시간(포맷팅), 처리 결과, 완료일
        * 첨부파일 섹션: 첨부된 파일 리스트, 다운로드 가능, **삭제 후 Issue 삭제 가능**
        * 변경 이력 섹션: 상태 변경, 담당자 변경, 심각도 변경, 상태 롤백 등 주요 변경사항 로그

* **US-8 (상태 관리):** MANAGER/담당자로서, 장애 상태를 "진행중" 또는 "완료"로 변경할 수 있다.
    * *Acceptance Criteria:*
        * 상태 드롭다운: 접수 → 진행중 → 완료 단방향 전이 가능
        * 상태 변경 시 변경일시 자동 기록
        * **COMPLETED → IN_PROGRESS 되돌리기 가능 (ADMIN만)**
        * **되돌리기 시 IssueHistory에 STATUS_ROLLBACK으로 기록**

* **US-9 (RBAC 적용):** ADMIN/MANAGER/USER 역할별로 접근 권한이 다르다.
    * *Acceptance Criteria:*
        * **ADMIN: 모든 장애 조회/수정/삭제 가능, 모든 부서 데이터 접근, 상태 롤백 가능**
        * **MANAGER: 같은 부서의 장애만 조회/수정, 담당자 할당(부서 내만)/변경(부서 내만)/완료 처리 가능**
        * **USER: 조회(자신 생성/담당 + 부서 공개), 신규 등록만 가능 (is_public 기반), IN_PROGRESS 상태 담당자 변경 불가**

* **US-10 (검색 및 필터):** USER로서, 다양한 조건(고객사, 상태, 심각도, 담당자, 기간)으로 장애를 검색할 수 있다.
    * *Acceptance Criteria:*
        * **동시에 여러 필터 적용 가능 (AND 조건)**
        * 필터 초기화 버튼으로 한 번에 모든 필터 제거
        * 검색 결과 카운트 표시 (예: "총 12건 중 3건 표시")

* **US-11 (ADMIN 상태 롤백):** ADMIN 역할로서, 실수로 완료된 장애를 다시 진행중 상태로 되돌릴 수 있다.
    * *Acceptance Criteria:*
        * 상태가 COMPLETED인 경우 [상태 되돌리기] 버튼 표시 (ADMIN만)
        * COMPLETED → IN_PROGRESS만 되돌리기 가능
        * 롤백 시 확인 다이얼로그: "이 Issue를 진행중 상태로 되돌리시겠습니까?"
        * IssueHistory에 STATUS_ROLLBACK으로 변경 이력 기록

## 4. Scope

### 4.1 In-Scope

* 장애 엔티티 정의 (`Issue` table) — 접수, 진행중, 완료 상태 관리
* **`is_public` 컬럼 추가 — 부서원 공개 여부 제어 (기본값: false)**
* 장애 목록 페이지 (`/issues`) — 필터링, 정렬, 페이지네이션 (권한별 행 필터링)
* 장애 상세 페이지 (`/issues/[id]`) — 조회, 수정, 상태 변경, **공개 여부 토글**
* 장애 신규 등록 페이지 (`/issues/new`) — 폼 검증, 저장
* 대시보드 요약 배지 — 상태별 카운트 (전체/진행중/완료), **AND 필터 조합**
* 필터 컴포넌트 — 고객사, 상태, 심각도, 담당자, 날짜 범위
* 파일 첨부 기능 — 장애별 결과 리포트 문서 관리 (최대 5개, 10MB each)
* **파일 검증 — 프론트엔드 + 서버 이중 검증 (MIME type, 확장자, 크기)**
* **ON DELETE RESTRICT 정책 — Issue 삭제 전 첨부파일 제거 필수**
* 변경 이력 로그 — 상태 변경, 담당자 변경, **심각도 변경, 상태 롤백, 파일 삭제 기록**
* **상태 롤백 기능 — ADMIN만 COMPLETED → IN_PROGRESS 가능**
* **처리 시간 입력 — 분 단위 단일 입력, 실시간 포맷팅 (2시간 30분)**
* API Route Handlers — CRUD 작업, **RBAC 검증, is_public 기반 행 필터링**
* TypeORM Entity — Issue, IssueAttachment, IssueHistory
* Oracle XE 21c 마이그레이션 — 테이블 생성 및 관계 설정

### 4.2 Out-of-Scope

* 실시간 알림 (장애 할당/완료 시 즉시 알림) — 별도 Notification PRD에서 다룰 예정
* 메일 발송 (담당자 할당 시 이메일 통지) — 별도 Email Integration PRD
* 통계 리포트/대시보드 분석 차트 — 별도 Analytics PRD
* 다국어 지원 (i18n)
* 모바일 전용 UI (< 768px 최적화는 일반 responsive 범위)
* 장애 관련 내부 채팅/협업 기능
* SLA 자동 계산 (응답 시간, 해결 시간 기한 설정)

## 5. Technical Considerations & Architecture Alignment

### 5.1 Next.js App Router Structure

* **Page Routes:**
    - `src/app/(main)/issues/page.tsx` — 장애 목록 페이지 (Server Component)
    - `src/app/(main)/issues/new/page.tsx` — 신규 등록 페이지 (Server Component, Client Components로 폼 감싸기)
    - `src/app/(main)/issues/[id]/page.tsx` — 상세 페이지 (Server Component)
    - `src/app/(main)/issues/loading.tsx` — 로딩 스켈레톤 UI

* **Layout:** 공통 `src/app/(main)/layout.tsx` 사용 (메인 쉘, 사이드바 + 헤더)

* **Server vs Client Components:**
    - 페이지 틀(`page.tsx`): Server Component — 세션/RBAC 검증, 초기 데이터 fetch
    - 목록/폼/상세 컴포넌트: Client Component ('use client') — interactivity, TanStack Query

### 5.2 API Route Handlers

* `GET /api/issues` — 목록 조회 (쿼리 파라미터: page, page_size, customer_id, status, severity, assignee_id, keyword, sort_by, sort_order)
  * **RBAC 기반 WHERE 절 동적 구성 (is_public 기반 행 필터링)**
* `POST /api/issues` — 신규 생성 (is_public 기본값: false)
* `GET /api/issues/[id]` — 상세 조회
* `PUT /api/issues/[id]` — 수정 (상태, 담당자, 처리 방법, 심각도, is_public 등)
  * **담당자 변경: MANAGER는 같은 부서만, IN_PROGRESS 상태에서도 가능**
  * **심각도 변경: MANAGER/ADMIN만, COMPLETED 제외**
* `DELETE /api/issues/[id]` — 소프트 삭제 (첨부파일 있으면 409 Conflict 응답)
* `PUT /api/issues/[id]/rollback` — 상태 되돌리기 (ADMIN만, COMPLETED → IN_PROGRESS)
* `POST /api/issues/[id]/attachments` — 파일 업로드 (서버 검증)
* `DELETE /api/issues/[id]/attachments/[attachmentId]` — 파일 삭제
* `GET /api/issues/summary` — 상태별 카운트 (필터 적용, RBAC 기반)

### 5.3 Database (Oracle XE 21c + TypeORM)

**Entity 정의:**

```
ISSUE 테이블:
├── id (PK, NUMBER, auto-increment via sequence)
├── customer_id (FK → CUSTOMER, ON DELETE RESTRICT)
├── title (VARCHAR2(255))
├── description (CLOB)
├── severity (VARCHAR2(20): CRITICAL / HIGH / MEDIUM / LOW)
├── status (VARCHAR2(20): INTAKE / IN_PROGRESS / COMPLETED)
├── is_public (NUMBER(1) DEFAULT 0) — NEW: 부서원 공개 여부
├── created_by_id (FK → EMPLOYEE)
├── assigned_to_id (FK → EMPLOYEE, nullable)
├── treatment_method (VARCHAR2(50): REMOTE / PHONE / ONSITE, nullable)
├── treatment_time_minutes (NUMBER, nullable) — 소요 시간 (분), 1~1440
├── treatment_result (CLOB, nullable)
├── created_at (TIMESTAMP, default SYSTIMESTAMP)
├── completed_at (TIMESTAMP, nullable)
├── updated_at (TIMESTAMP, default SYSTIMESTAMP)
└── deleted_at (TIMESTAMP, nullable) — soft delete

ISSUE_ATTACHMENT 테이블:
├── id (PK)
├── issue_id (FK → ISSUE, ON DELETE RESTRICT) — CHANGED: CASCADE → RESTRICT
├── file_name (VARCHAR2(255))
├── file_path (VARCHAR2(512))
├── file_size (NUMBER)
├── uploaded_by_id (FK → EMPLOYEE)
├── created_at (TIMESTAMP)
└── deleted_at (TIMESTAMP)

ISSUE_HISTORY 테이블:
├── id (PK)
├── issue_id (FK → ISSUE)
├── change_type (VARCHAR2(50): STATUS_CHANGE / ASSIGNEE_CHANGE / SEVERITY_CHANGE / STATUS_ROLLBACK / ATTACHMENT_UPLOADED / ATTACHMENT_DELETED / COMMENT_ADDED) — UPDATED: 타입 확장
├── old_value (VARCHAR2(255))
├── new_value (VARCHAR2(255))
├── changed_by_id (FK → EMPLOYEE)
├── changed_at (TIMESTAMP)
└── remark (CLOB, nullable)
```

**외래키 관계:**
- ISSUE.customer_id → CUSTOMER.id (ON DELETE RESTRICT)
- ISSUE.created_by_id → EMPLOYEE.id
- ISSUE.assigned_to_id → EMPLOYEE.id
- ISSUE_ATTACHMENT.issue_id → ISSUE.id (ON DELETE RESTRICT) — **CHANGED**
- ISSUE_ATTACHMENT.uploaded_by_id → EMPLOYEE.id
- ISSUE_HISTORY.issue_id → ISSUE.id
- ISSUE_HISTORY.changed_by_id → EMPLOYEE.id

**Oracle 규칙 준수:**
- 모든 identifier는 double-quote 사용 (`"ISSUE"`, `"customer_id"`)
- `VARCHAR2`, `NUMBER`, `CLOB` 타입만 사용
- **`ON DELETE RESTRICT` 적용 (CASCADE 금지) — sunjin-erp 정책**
- 모든 테이블에 `deleted_at` 컬럼으로 소프트 삭제
- Sequence 생성: `CREATE SEQUENCE issue_id_seq START WITH 1 INCREMENT BY 1`

### 5.4 State Management

* **Server State:** TanStack Query (React Query)
    - `useIssueListQuery(params)` — 목록 조회 및 캐싱 (RBAC 기반)
    - `useIssueDetailQuery(id)` — 상세 조회
    - `useIssueSummaryQuery()` — 상태별 카운트
    - Query Key Factory 패턴 사용

* **Client State:** Zustand (필터 임시 상태, 페이지 번호 등)
    - `useIssueFilterStore` — 필터 상태 (customer_id, status, severity 등)
    - `usePaginationStore` — 현재 페이지

* **Form State:** React Hook Form + Zod validation

### 5.5 Authentication & Authorization (RBAC)

* **NextAuth.js Session:** `session.user.role` (ADMIN / MANAGER / USER), `session.user.department_id`

* **미들웨어:** `/issues` 경로 접근 시 인증 확인 (middleware.ts)

* **API Route 검증:**

**ADMIN:**
- 모든 데이터 조회/수정/삭제 가능
- 상태 되돌리기 가능 (COMPLETED → IN_PROGRESS)
- 심각도 변경 가능
- 모든 직원에게 담당자 할당 가능

**MANAGER:**
- 같은 부서 장애만 조회/수정
- 부서 내 직원에게만 담당자 할당 가능 (부서 제약)
- IN_PROGRESS 상태에서도 담당자 변경 가능 (부서 내만)
- 심각도 변경 가능 (완료 제외)
- 상태 변경 가능 (할당, 완료)

**USER:**
- 조회: 자신이 생성한 Issue + 자신에게 할당된 Issue + 같은 부서의 공개 Issue (is_public=true)
- 신규 등록 가능 (is_public 기본값: false)
- 담당자 변경 불가 (IN_PROGRESS 포함)
- 심각도 변경 불가
- 상태 변경 불가

* **행 수준 보안 (RLS):**
    - API GET /issues에서 WHERE 절 동적 구성
    - ADMIN: 모든 행 반환
    - MANAGER: 같은 부서 (assigned_to_id의 부서) 데이터만
    - USER: 자신 생성 + 자신 담당 + 같은 부서 공개(is_public=true) 데이터만

### 5.6 파일 첨부 관리

* **저장 위치:** `UPLOAD_DIR` 환경 변수 (기본 `./uploads/issues`)
* **파일 명명:** `{issueId}_{timestamp}_{originalFilename}`
* **허용 포맷:** `.pdf`, `.xlsx`, `.docx`, `.pptx`, `.jpg`, `.png`, `.gif` 등
* **제한 사항:**
    - 파일당 최대 10MB
    - 장애당 최대 5개 파일
    - **삭제 정책: ON DELETE RESTRICT (Issue 삭제 전 파일 제거 필수)**
* **검증:**
    - **프론트엔드: 파일 선택 시 실시간 검증 (MIME type, 크기) — 즉시 피드백**
    - **서버: 업로드 시 재검증 (MIME type, 확장자, 크기, 개수) — 보안**

### 5.7 검색 및 필터링

* **쿼리 파라미터:**
    - `page` (기본 1)
    - `page_size` (기본 20, 최대 100)
    - `customer_id` (optional)
    - `status` (optional, 다중 선택 가능)
    - `severity` (optional, 다중 선택 가능)
    - `assignee_id` (optional)
    - `created_by_id` (optional)
    - `date_from`, `date_to` (optional, 생성일 범위)
    - `keyword` (optional, 제목/설명 검색)
    - `sort_by` (기본 created_at, 옵션: status, severity, assigned_to_id)
    - `sort_order` (기본 DESC)

* **SQL WHERE 절 동적 생성:**
    - **모든 필터를 AND 조합으로 적용 (배지 클릭 포함)**
    - RBAC 기반 필터링 자동 적용 (is_public 기반)
    - LIKE 검색 (keyword)

## 8. Security Considerations

* **Authentication:** NextAuth.js 세션 기반, 모든 API route 보호
    - 미인증 사용자 접근 시 401 → `/login` 리다이렉트
    - 세션 만료 시 TanStack Query 에러 핸들러에서 자동 리다이렉트

* **Authorization (RBAC):**
    - API route에서 session.user.role 확인 후 처리
    - **is_public 기반 행 수준 필터링 (RLS)**
    - ADMIN: 제한 없음
    - MANAGER: 같은 부서 장애만 조회/수정, 부서 내 담당자만 할당 (부서 제약)
    - USER: 조회(자신 생성/담당 + 부서 공개), 신규 등록, 수정/삭제 불가
    - 권한 없는 접근 시 403 Forbidden 응답

* **Input Validation:**
    - 클라이언트: React Hook Form + Zod로 폼 검증 + 파일 검증
    - 서버: 모든 input 재검증 (SQL injection, XSS 방지)
    - **파일 업로드: MIME type 검증(이중), 확장자 화이트리스트, 파일 크기 제한(이중)**

* **Data Protection:**
    - CLOB 필드(설명, 처리 결과)는 비암호화 저장 (내부망 한정이므로)
    - 민감한 고객 정보는 조회 권한 제한 (is_public 플래그)
    - 감시 감사 로그: 주요 변경사항(상태, 담당자, 심각도, 롤백) 기록

* **SQL Injection 방지:**
    - TypeORM 파라미터 바인딩 사용 (`:parameterName`)
    - Raw SQL 사용 시 항상 파라미터화된 쿼리 작성

* **XSS 방지:**
    - React 템플릿 엔진의 자동 escape ({{ }} 사용)
    - dangerouslySetInnerHTML 사용 금지
    - 사용자 입력 항상 sanitize

* **파일 첨부 보안:**
    - 파일 업로드 경로 접근 제한 (Next.js API route 경유만)
    - 파일명 난독화 (타임스탐프 + ID 기반)
    - **서버 검증 재실시 (클라이언트 우회 방지)**
    - **ON DELETE RESTRICT 정책: Issue 삭제 전 파일 제거 강제 (증거 보존)**
