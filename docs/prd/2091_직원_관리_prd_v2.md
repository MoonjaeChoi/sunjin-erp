## 1. Overview

본 PRD는 sunjin-erp 시스템의 "직원 관리 (인사)" 기능에 대한 요구사항을 정의한다.
이 기능은 조직 구조(부서, 직급), 직원 기본 정보(이름, 연락처, 직책), 계정 권한(로그인 아이디, 암호, 역할)을 통합적으로 관리하며, ADMIN은 전체 직원에 대한 CRUD 권한을, MANAGER는 자신의 부서 내 직원 정보를 읽기 전용으로 조회할 수 있는 직원/인사 관리 시스템을 제공한다.

**대상 모듈:** 직원 관리 (인사)
**대상 사용자 역할:** ADMIN (전체 관리), MANAGER (부서별 읽기 전용)

## 2. Goals & Objectives

* **조직 구조 정의:** 부서(Department) 및 직급(Position) 체계를 구축하여 조직 계층과 역할을 명확하게 정의
* **직원 정보 통합 관리:** 직원의 기본 정보(이름, 이메일, 전화, 입사일, 부서, 직급)를 단일 시스템에서 관리
* **계정 권한 관리:** 직원별 로그인 계정(username), 암호(password), 시스템 역할(ADMIN/MANAGER/USER)을 엄격하게 관리
* **권한 기반 조직 조회:** MANAGER는 자신의 정확한 부서 소속 직원만 조회 가능 (하위 부서 제외), ADMIN은 전체 조직 조회 가능 [UPDATED: MANAGER 권한 범위 명확화 (Decision 1)]
* **감사 추적:** 직원 정보 및 권한 변경 이력을 기록하여 컴플라이언스 요구사항 충족 [UPDATED: 생성자/변경자 정보 보존 강화 (Decision 3)]
* **비활성화 관리:** 퇴사한 직원을 계정 비활성화 또는 소프트 삭제로 관리하여 로그인 차단 및 과거 업무 이력 유지 [UPDATED: 이중 메커니즘 명확화 (Decision 2)]
* **조직도 조회:** 부서별 인원 현황 및 조직 계층도 시각화 (Phase 2)

## 3. User Stories / Use Cases

* **US-1:** 시스템 관리자로서, 새로운 부서(Department)를 등록할 수 있다. 그래서 조직 구조를 체계적으로 관리할 수 있다.
    * *Acceptance Criteria:*
        * 부서 관리 페이지에서 부서명, 부서 코드, 상위 부서(parent department) 선택 가능
        * 부서명 중복 검증 (soft delete 제외)
        * 부서 등록 후 즉시 직원 배치에 사용 가능
        * 부서 삭제 시 다음 두 조건을 모두 만족할 때만 삭제 가능: (1) 소속 직원 없음 (deleted_at IS NULL), (2) 자식 부서 없음 [UPDATED: 부서 삭제 조건 강화 (Decision 7)]
        * 부서 변경 이력 기록
        * 부서 계층은 최대 5단계로 제한, 순환 참조 불가 [UPDATED: 계층 깊이 제한 (Decision 4, 12)]

* **US-2:** 시스템 관리자로서, 직급(Position) 체계를 정의할 수 있다. 그래서 조직 내 역할 계층을 명확하게 할 수 있다.
    * *Acceptance Criteria:*
        * 직급 관리 페이지에서 직급명, 직급 레벨(1~10) 정의 가능
        * 직급 코드 자동 생성 (POS-{5digit}, Oracle SEQUENCE 사용) [UPDATED: 동시성 보증 방식 명시 (Decision 10)]
        * 직급 삭제 시 소속 직원이 없는 경우에만 삭제 가능
        * 직급 변경 이력 기록

* **US-3:** 시스템 관리자로서, 신규 직원의 기본 정보(이름, 연락처, 입사일, 부서, 직급)를 등록할 수 있다. 그래서 직원의 기본 정보를 시스템에 등록할 수 있다.
    * *Acceptance Criteria:*
        * 직원 등록 폼에서 필수 필드: 이름, 이메일, 전화, 부서, 직급, 입사일
        * 선택 필드: 직무 설명(description), 상위 매니저(manager_id)
        * 이메일 중복 검증 (soft delete 제외, 회사 이메일)
        * 전화번호 형식 검증 (한국 표준)
        * 부서/직급은 드롭다운으로 선택
        * 등록 성공 후 계정 생성 페이지로 자동 이동

* **US-4:** 시스템 관리자로서, 직원의 계정(username, password, role)을 생성 및 관리할 수 있다. 그래서 직원이 시스템에 로그인할 수 있다.
    * *Acceptance Criteria:*
        * 계정 생성 폼에서 username(이메일 기반, 자동 입력), 임시 암호 설정 가능
        * Phase 1: 관리자가 임시 암호를 수동으로 설정하고 UI에 일회 표시 (Decision 5)
        * Phase 2: 암호 재설정 링크 발급 기능 (별도 인증 PRD)
        * 암호는 bcrypt 해시하여 저장, 평문 저장 금지
        * 직원별 시스템 역할(ADMIN/MANAGER/USER) 지정 가능
        * 계정 활성화/비활성화 토글 가능 (계정 삭제 아님)
        * 암호 변경 이력 기록 (평문 저장 금지, 변경 시각만 기록)
        * 권한 변경 이력 기록

* **US-5:** 시스템 관리자로서, 직원 목록을 조회하고 필터링(부서, 직급, 활성 상태)할 수 있다. 그래서 조직 현황을 파악할 수 있다.
    * *Acceptance Criteria:*
        * 직원 목록 페이지에서 이름, 이메일 검색 가능
        * 부서, 직급, 활성 상태(활성/비활성) 필터링 가능
        * 목록에 표시: 이름, 부서, 직급, 이메일, 입사일, 계정 활성 여부
        * 페이지네이션 지원 (20개 항목 기본, 최대 100)
        * 정렬 지원: 이름, 입사일, 부서 등

* **US-6:** 매니저로서, 자신의 정확한 부서에 속한 직원의 기본 정보(이름, 연락처, 직급, 입사일)를 읽기 전용으로 조회할 수 있다. 그래서 팀 구성원을 빠르게 확인할 수 있다. [UPDATED: 부서 범위 명확화 (Decision 1)]
    * *Acceptance Criteria:*
        * 직원 목록 필터가 자동으로 자신의 정확한 부서로 제한됨 (하위 부서 제외) [UPDATED: MANAGER 권한 범위 (Decision 1)]
        * 다른 부서 직원은 조회 불가 (API 403 또는 404)
        * 상세 페이지 열람 가능하나, 수정 버튼 비활성화
        * 계정 정보(role, password 등)는 조회 불가

* **US-7:** 시스템 관리자로서, 직원의 기본 정보(이름, 연락처, 부서, 직급, 직무)를 수정할 수 있다.
    * *Acceptance Criteria:*
        * 직원 상세 페이지에서 기본 정보 수정 가능 (ADMIN만)
        * 수정 시 변경 사항만 기록 (필드 + 이전값 → 새로운값)
        * 부서/직급 변경 시 이력에 명시
        * 수정자, 수정 시각 기록

* **US-8:** 시스템 관리자로서, 퇴사한 직원을 비활성화하여 로그인을 차단할 수 있다. 그래서 보안을 유지하면서도 과거 업무 이력은 유지할 수 있다.
    * *Acceptance Criteria:*
        * 직원 상세 페이지에 "계정 비활성화" 버튼 제공 (또는 상태 토글)
        * 비활성화 시 Account.is_active = false로 설정, 직원 정보는 유지 (deleted_at은 변경 안 함)
        * 소프트 삭제와 구분: 계정 비활성화(is_active=false)는 로그인만 차단, 소프트 삭제(deleted_at)는 기록 제외 [UPDATED: 이중 메커니즘 명확화 (Decision 2)]
        * 비활성화된 직원은 로그인 불가 (인증 시 체크: Account.is_active=true AND Employee.deleted_at IS NULL) [UPDATED: 로그인 검증 체크리스트 (Decision 11)]
        * 과거 프로젝트/기술지원 이력은 유지됨
        * 비활성화 이력 기록

* **US-9:** 시스템 관리자로서, 직원 정보 변경 이력(생성, 수정, 삭제)을 조회할 수 있다. 그래서 감사(audit) 추적이 가능하다.
    * *Acceptance Criteria:*
        * 직원 상세 페이지에 "변경 이력" 탭 제공
        * 이력에는 변경 유형(CREATE/UPDATE/DELETE), 변경자, 변경 시각, 변경 필드 기록
        * 변경자 정보는 ON DELETE RESTRICT로 보존 [UPDATED: 감사 추적 신뢰성 강화 (Decision 3)]
        * 권한 변경, 부서 변경, 계정 비활성화 등도 이력에 기록
        * 시스템 관리자만 조회 가능

* **US-10:** 시스템 관리자로서, 직원 정보 및 계정을 완전히 삭제할 수 있다. 그래서 테스트 계정 등을 정리할 수 있다.
    * *Acceptance Criteria:*
        * 직원 상세 페이지에 "완전 삭제" 옵션 제공 (관리자 전용, 부드러운 UI 경고)
        * 삭제 시 확인 대화 표시
        * hard delete 시 모든 FK 참조 검증: Project, TechSupport, Task, Issue, Account, EmployeeHistory 등 [UPDATED: 의존성 검증 강화 (Decision 6)]
        * 의존성 있으면 명확한 에러 메시지: "이 직원은 5개 프로젝트에서 담당자입니다..." [UPDATED: 에러 메시지 상세화 (Decision 6)]
        * 삭제는 hard delete (복구 불가)

## 4. Scope

### 4.1 In-Scope

* **Department (부서) Entity**
    - 부서명(name), 부서 코드(code), 설명(description)
    - 상위 부서(parent_department_id, FK, 계층 구조 지원)
    - 메타데이터: created_at, updated_at, deleted_at (soft delete)
    - Unique constraint on code (soft delete 제외)
    - **[UPDATED Decision 4, 12]** 부서 계층 제약:
      - 최대 깊이: 5단계
      - 순환 참조 방지: parent_department_id 변경 시 검증
      - 삭제 조건: 자식 부서 없음 AND 활성 직원 없음

* **Position (직급) Entity**
    - 직급명(name), 직급 코드(code, auto-generated: POS-{5digit} via Oracle SEQUENCE), 직급 레벨(level: 1~10)
    - 메타데이터: created_at, updated_at, deleted_at (soft delete)
    - **[UPDATED Decision 10]** 코드 생성: Oracle SEQUENCE로 동시성 보증

* **Employee (직원) Entity**
    - 기본 정보: 이름(name), 이메일(email), 전화(phone), 직무(job_title)
    - 조직 정보: 부서 FK, 직급 FK, 상위 매니저 FK (nullable)
    - 입사일(hired_at), 생일(birthday, 선택사항)
    - 메타데이터: created_at, created_by_id, updated_at, updated_by_id, deleted_at
    - Unique constraint on email (soft delete 제외)
    - **[UPDATED Decision 3]** created_by_id, updated_by_id: ON DELETE RESTRICT (감사 추적 신뢰성)

* **Account (계정) Entity**
    - 직원 FK (ON DELETE RESTRICT)
    - username(unique, FK from email 또는 수동 입력)
    - password (bcrypt hashed, never plain text)
    - role (VARCHAR2: 'ADMIN', 'MANAGER', 'USER')
    - is_active (boolean, default: true, 로그인 차단 용)
    - last_login_at (timestamp, nullable)
    - password_changed_at (timestamp)
    - metadata: created_at, updated_at, deleted_at (soft delete)
    - Unique constraint on username (soft delete 제외)
    - **[UPDATED Decision 2]** 의미: is_active=false이면 로그인 불가, Employee.deleted_at과 독립적

* **EmployeeHistory (직원 감사 로그) Entity**
    - 직원 FK (ON DELETE RESTRICT)
    - change_type (VARCHAR2: 'CREATE' | 'UPDATE' | 'DELETE' | 'DEACTIVATE')
    - changed_fields (CLOB, JSON: {"fieldName": {"before": value, "after": value}})
    - changed_by_id FK (who made the change, **ON DELETE RESTRICT**)
    - changed_at (timestamp)
    - 불변 로그 (soft delete 없음)
    - **[UPDATED Decision 3]** changed_by_id: ON DELETE RESTRICT

* **API Route Handlers (14개)**
    - Department: GET (list), POST (create), PUT (update, 순환참조/깊이 검증), DELETE (자식부서/직원 검증)
    - Position: GET (list), POST (create), PUT (update), DELETE (soft delete)
    - Employee: GET (list), POST (create), GET (detail), PUT (update), DELETE (hard delete, 모든 의존성 검증)
    - Account: POST (create), PUT (change role), POST (disable/enable)
    - EmployeeHistory: GET (detail history)
    - **[UPDATED Decision 6, 7]** 상세한 의존성 검증 및 에러 응답

* **Frontend Pages & Components**
    - 직원 목록 페이지 (`/employees`)
    - 직원 상세 페이지 (`/employees/[id]`)
    - 직원 등록 페이지 (`/employees/new`)
    - 부서 관리 페이지 (`/employees/departments`)
    - 직급 관리 페이지 (`/employees/positions`)
    - EmployeeList 컴포넌트 (테이블, 필터, 검색)
    - EmployeeForm 컴포넌트 (등록/수정 폼)
    - EmployeeDetail 컴포넌트 (기본정보 + 계정 + 이력)
    - AccountForm 컴포넌트 (계정 생성/권한 변경)
    - DepartmentManager 컴포넌트 (부서 CRUD)
    - PositionManager 컴포넌트 (직급 CRUD)

* **TanStack Query Hooks**
    - `useEmployees()` — 목록 조회 (부서별 필터링 포함)
    - `useEmployee(id)` — 상세 조회
    - `useCreateEmployee()` — 신규 등록 mutation
    - `useUpdateEmployee(id)` — 수정 mutation
    - `useDeleteEmployee(id)` — 완전 삭제 mutation (의존성 검증)
    - `useDeactivateEmployee(id)` — 계정 비활성화 mutation
    - `useCreateAccount(employeeId)` — 계정 생성 mutation
    - `useUpdateAccountRole(accountId)` — 권한 변경 mutation
    - `useDepartments()` — 부서 목록
    - `usePositions()` — 직급 목록
    - `useEmployeeHistory(employeeId)` — 이력 조회

* **역할 기반 접근 제어 (RBAC)**
    - ADMIN: 전체 직원 CRUD, 계정 관리, 부서/직급 관리, 이력 조회
    - MANAGER: **[UPDATED Decision 1, 9]** 자신의 정확한 부서 직원 정보만 읽기 전용 조회 (수정 불가), 계정 관리 불가, 하위 부서는 조회 불가
    - USER: 직원 관리 메뉴 미표시

* **유효성 검증**
    - 이름: 필수, 100자 이내
    - 이메일: 필수, 회사 도메인 또는 제한 없음, 고유성 검증
    - 전화번호: 한국 표준 형식 (02-xxxx-xxxx, 010-xxxx-xxxx, 등)
    - 입사일: 필수, 미래 날짜 불가
    - 부서/직급: 필수, enum 체크
    - username: 필수, 고유성, 6~20자, 영문+숫자 (특수문자 제한)
    - password: 최소 8자, 영문+숫자+특수문자 포함 (보안 정책)
    - 부서명 중복 검증, 직급명 중복 검증

* **캐시 무효화 전략** [UPDATED Decision 8]
    - 세분화된 부분 무효화 (또는 보수적 전체 무효화):
      - 직원 추가/수정/비활성화 시: 해당 직원 detail 캐시 즉시 업데이트, list 캐시는 부분 무효화
      - 부서 추가/수정/삭제 시: departments, employees-list 캐시 무효화
      - 직급 추가/수정/삭제 시: positions, employees-list 캐시 무효화
      - 부분 무효화 지원 (특정 직원/부서/직급의 캐시만 무효화)

* **부서 기반 권한 필터링 (RBAC Scoping)** [UPDATED Decision 1]

### 5.3 Database (Oracle XE 21c + Direct oracledb)

> **⚠️ 중요**: TypeORM 0.3.28은 Next.js 14 strict mode 호환성 문제로 2026-01-27부터 완전히 제거되었습니다.
> 모든 데이터베이스 쿼리는 `src/lib/db-direct.ts`의 `executeQuery` (SELECT) 및 `executeUpdate` (INSERT/UPDATE/DELETE) 함수를 사용합니다.
> 상세 내용: `docs/operation/011_데이터베이스연결.md` 참조

**Entity 정의:**

```
DEPARTMENT (부서)
├── id (PK)
├── name (VARCHAR2, UNIQUE on non-deleted)
├── code (VARCHAR2, UNIQUE, e.g., "IT", "SALES")
├── description (VARCHAR2)
├── parent_department_id (FK → DEPARTMENT, nullable, ON DELETE RESTRICT)
├── created_at (TIMESTAMP)
├── updated_at (TIMESTAMP)
├── deleted_at (TIMESTAMP, soft delete)
└── Indexes:
    ├── PRIMARY KEY (id)
    ├── UNIQUE (name) WHERE deleted_at IS NULL
    ├── UNIQUE (code) WHERE deleted_at IS NULL
    ├── (parent_department_id)
    ├── (created_at)
    ├── (deleted_at)
├── [UPDATED Decision 4, 12] 제약:
    ├── 최대 깊이: 5단계
    ├── 순환 참조 방지 (API 레벨)

POSITION (직급)
├── id (PK)
├── name (VARCHAR2, UNIQUE on non-deleted)
├── code (VARCHAR2, auto-generated via SEQUENCE: POS-{5digit}, UNIQUE)
├── level (NUMBER, 1-10)
├── created_at (TIMESTAMP)
├── updated_at (TIMESTAMP)
├── deleted_at (TIMESTAMP, soft delete)
└── Indexes:
    ├── PRIMARY KEY (id)
    ├── UNIQUE (name) WHERE deleted_at IS NULL
    ├── UNIQUE (code)
    ├── (level)
    ├── (deleted_at)
├── [UPDATED Decision 10] Oracle SEQUENCE:
    └── POSITION_CODE_SEQ for auto-increment

EMPLOYEE (직원)
├── id (PK)
├── name (VARCHAR2)
├── email (VARCHAR2, UNIQUE on non-deleted)
├── phone (VARCHAR2)
├── job_title (VARCHAR2)
├── department_id (FK → DEPARTMENT, ON DELETE RESTRICT)
├── position_id (FK → POSITION, ON DELETE RESTRICT)
├── manager_id (FK → EMPLOYEE, nullable, ON DELETE SET NULL)
├── hired_at (TIMESTAMP)
├── birthday (TIMESTAMP, nullable)
├── created_at (TIMESTAMP)
├── created_by_id (FK → EMPLOYEE, [UPDATED Decision 3] ON DELETE RESTRICT)
├── updated_at (TIMESTAMP)
├── updated_by_id (FK → EMPLOYEE, [UPDATED Decision 3] ON DELETE RESTRICT)
├── deleted_at (TIMESTAMP, soft delete)
├── [열 식별자 규칙] 소문자 quoted identifier 사용:
│   └── "id", "name", "email", "phone", "job_title", "hired_at", "birthday",
│       "created_at", "created_by_id", "updated_at", "updated_by_id", "deleted_at"
│   └── DEPARTMENT_ID, POSITION_ID, MANAGER_ID (대문자, unquoted)
└── Indexes:
    ├── PRIMARY KEY (id)
    ├── UNIQUE (email) WHERE deleted_at IS NULL
    ├── (department_id)
    ├── (position_id)
    ├── (manager_id)
    ├── (hired_at)
    ├── (deleted_at)

ACCOUNT (계정)
├── id (PK)
├── employee_id (FK → EMPLOYEE, UNIQUE, ON DELETE RESTRICT)
├── username (VARCHAR2, UNIQUE on non-deleted)
├── password (VARCHAR2, bcrypt hashed, never plain text)
├── role (VARCHAR2: 'ADMIN' | 'MANAGER' | 'USER')
├── is_active (BOOLEAN, default: true, [UPDATED Decision 2] 로그인 차단용)

├── password_changed_at (TIMESTAMP)
├── created_at (TIMESTAMP)
├── updated_at (TIMESTAMP)
├── deleted_at (TIMESTAMP, soft delete for deactivated accounts)

    ├── PRIMARY KEY (id)
    ├── UNIQUE (employee_id)
    ├── UNIQUE (username) WHERE deleted_at IS NULL
    ├── (is_active)
    ├── (role)
    ├── (deleted_at)

EMPLOYEE_HISTORY (감사 로그)
├── id (PK)
├── employee_id (FK → EMPLOYEE, ON DELETE RESTRICT)
├── change_type (VARCHAR2: 'CREATE' | 'UPDATE' | 'DELETE' | 'DEACTIVATE')
├── changed_fields (CLOB, JSON: {"fieldName": {"before": old, "after": new}})
├── changed_by_id (FK → EMPLOYEE, [UPDATED Decision 3] ON DELETE RESTRICT)
├── changed_at (TIMESTAMP)
└── Indexes:

    ├── (employee_id)
    ├── (changed_at)
    ├── (change_type)
```

**Constraints:**
- `ON DELETE RESTRICT` for critical foreign keys: department, position, created_by, updated_by, changed_by [UPDATED Decision 3]
- `ON DELETE SET NULL` for optional references (manager)
- Unique constraints with `deleted_at IS NULL` (partial unique index)
- Check constraint on `POSITION.level` (1-10)
- Check constraint on `ACCOUNT.role` ('ADMIN', 'MANAGER', 'USER')
- **[UPDATED Decision 4, 12]** Department depth constraint (max 5 levels, checked at API level)

```typescript
import { executeQuery } from '@/lib/db-direct';

const result = await executeQuery(
```

```typescript
import { executeUpdate } from '@/lib/db-direct';
```

**Oracle RETURNING 제한:**
- Oracle에서 `RETURNING ... INTO :bindVar` 형식 필요 (PostgreSQL과 다름)
- 권장 패턴: INSERT 실행 후 별도 SELECT로 생성된 레코드 조회
```typescript
// 1. INSERT 실행
await executeUpdate(insertSql, params);
// 2. 생성된 레코드 조회 (unique key로)
const result = await executeQuery(selectSql, { code: generatedCode });
```

**열 식별자 케이싱:**

### 5.7 암호 보안 정책

* **해시 알고리즘:** bcrypt (salt rounds: 10+)
* **저장 규칙:** 평문 저장 금지, 모든 암호는 bcrypt 해시
* **검증:** 로그인 시 bcrypt.compare() 사용
* **변경 이력:** 암호 변경 시각만 기록 (평문이나 해시 저장 금지)
* **임시 암호 (Phase 1):** [UPDATED Decision 5] 관리자가 수동으로 설정, UI에 일회 표시 (최소 8자, 영문+숫자+특수문자)
* **암호 재설정 (Phase 2):** 일회용 재설정 링크 발급 (별도 인증 PRD)

### 5.8 부서 기반 권한 필터링 (MANAGER 권한) [UPDATED Decision 1]

* **MANAGER 접근 제한:**
    - 자신의 정확한 부서(`session.user.department_id`)에만 접근 권한 (하위 부서 제외)
    - 다른 부서 직원 조회 시 API 403 또는 404 응답
    - 상세 페이지: 수정, 삭제, 계정 관리 버튼 비활성화
    - 계정 정보(role, password) 조회 불가

* **API 필터링:**
    ```
    MANAGER: GET /api/employees?department_id={session.user.department_id}
    → 자신의 정확한 부서 직원만 반환 (하위 부서는 제외)
    ```

* **조회 시 권한 검증:**
    - ADMIN: 모든 직원 상세 정보 조회 가능
    - MANAGER: 자신의 정확한 부서 직원만 조회 가능 (계정 정보 제외, 하위 부서 제외) [UPDATED: 범위 명시]
    - USER: 직원 관리 메뉴 미표시

### 5.9 입력 검증 및 보안

* **Server-side 검증 (필수):**
    - 이름: 필수, 100자 이내, XSS 방지
    - 이메일: 정규식 검증 (RFC 5322), 고유성 검증
    - 전화번호: 한국 표준 형식 검증
    - 입사일: 과거 날짜만 허용
    - username: 6~20자, 영문+숫자만, 고유성
    - password: 최소 8자, 영문+숫자+특수문자, bcrypt 해시
    - role: enum 검증 ('ADMIN', 'MANAGER', 'USER')
    - 부서/직급 FK 검증
    - **[UPDATED Decision 4, 12]** 부서 계층: 깊이 제한 (max 5), 순환 참조 방지

* **Client-side 검증:**
    - React Hook Form으로 실시간 피드백

* **SQL Injection 방지:**
    - oracledb bind parameters 사용 (`:paramName` 형식)

* **CSRF 방지:**
    - NextAuth.js 자동 처리

### 5.10 성능 최적화

* **API Response Time Target:** p95 < 200ms
* **Pagination:** 기본 20개, 최대 100개 (성능 제약)
* **Index Strategy:**
    - `EMPLOYEE(email)` — 로그인/검색
    - `EMPLOYEE(department_id)` — 부서별 필터링
    - `EMPLOYEE(position_id)` — 직급별 필터링
    - `EMPLOYEE(hired_at)` — 입사일 정렬
    - `ACCOUNT(username)` — 로그인
    - `ACCOUNT(employee_id, is_active)` — 계정 활성화 검증
    - `DEPARTMENT(parent_department_id)` — 계층 구조 조회
    - `EMPLOYEE_HISTORY(employee_id, changed_at)` — 이력 조회

* **Lazy Loading:**
    - 계정 정보는 상세 페이지에서만 별도 쿼리 (list에 포함 안 함)
    - 이력은 별도 탭에서 필요할 때만 조회

## 8. Security Considerations

* **Authentication:** NextAuth.js session 기반, 모든 API 호출 전 세션 검증
* **Authorization:**
    - ADMIN: 전체 직원 CRUD, 계정 관리, 부서/직급 관리, 이력 조회
    - MANAGER: 자신의 정확한 부서 직원만 읽기 전용 조회 (하위 부서 제외) [UPDATED Decision 1, 9]
    - API 레벨에서 권한 검증 (프론트엔드 숨김만으로 불충분)

* **Encryption & Password Security:**
    - 모든 암호는 bcrypt로 해시 (평문 저장 금지)
    - HTTPS/TLS로 전송 암호화
    - 암호 변경 이력: 변경 시각만 기록 (해시 저장 금지)

* **Input Validation:**
    - Server-side 검증 필수 (모든 입력값)
    - XSS 방지: 사용자 입력 sanitization
    - SQL Injection 방지: TypeORM parameterized queries
    - 이메일, 전화번호 형식 검증

* **Audit Trail:**
    - 모든 직원 CRUD 작업 기록
    - 권한 변경, 계정 비활성화, 부서 변경 이력
    - 변경자, 변경 시각, 변경 내용 기록
    - **[UPDATED Decision 3]** 생성자/변경자 정보 ON DELETE RESTRICT로 보존

* **Data Protection:**
    - 직원 기본 정보(이메일, 전화) 민감 데이터 취급
    - 계정 정보(username, role)는 ADMIN만 조회 가능
    - 로그: 민감정보 마스킹 (이메일 일부, 전화번호 일부)

* **CSRF 방지:**
    - NextAuth.js에서 자동 처리

* **로그인 검증:** [UPDATED Decision 11]
    - 명시적 체크리스트 (Account 존재 → is_active → Employee 존재 → deleted_at → 암호)
    - 각 실패 시 적절한 메시지 또는 통일된 에러

### 9.2 Key Changes Summary

**Database Schema:**
- `created_by_id`, `updated_by_id`: ON DELETE RESTRICT 변경
- `changed_by_id`: ON DELETE RESTRICT 설정
- Department 계층 깊이 제한: 5단계 (애플리케이션 레벨)

**API Enhancements:**
- DELETE /api/employees/[id]: 모든 FK 참조 검증, 상세 에러 메시지

**Phasing:**
- Phase 1: 수동 임시 암호 + 읽기 전용 MANAGER

## 11. Open Questions & Resolved Issues

### Resolved (의존성 제거)

* **Q1:** 부서 계층 구조(parent_department_id)의 깊이 제한이 있는가?
    - **해결:** 최대 5단계로 제한 (Decision 4, 12)

* **Q2:** 직원 삭제 시 관련 프로젝트/기술지원 기록이 있으면 어떻게 처리할 것인가?
    - **해결:** 모든 FK 참조 검증 후 상세 에러 메시지 반환 (Decision 6)

* **Q3:** 암호 정책의 최소 요구사항은 무엇인가?
    - **해결:** 최소 8자, 영문+숫자+특수문자 포함 (기존 유지)

* **Q4:** 비활성화와 soft delete의 차이를 명확히 할 필요가 있는가?
    - **해결:** 이중 메커니즘 명확화 (Decision 2)
      - Account.is_active = false: 로그인만 차단, 직원 레코드 유지
      - Employee.deleted_at ≠ null: 목록 제외, 관리자만 복구 가능
      - hard delete: 의존성 없을 시만 물리 삭제
